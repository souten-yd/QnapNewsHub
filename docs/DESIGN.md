# QNAP ニュースハブ（QnapNewsHub）の設計

2026-11-24 利用者の決定（B 案）:
- 「QNAP ニュースハブと名前します」。ずっと電源の入っている QNAP（非力）で、ニュースを **集める・ためる・読む** を受け持つ。
- ControlDeck（メインの PC。電源を切ることがある）は **サブ**。必要なデータだけをニュースハブから抽出して使い、ニュースハブが止まっているときだけ自分で集める。ControlDeck のニュースの機能は最低限を持ち、機能の有効・無効を News の設定で変えられる。
- ニュースハブでも、ControlDeck と同じようなグラフィカルな画面でニュースを読める。画像が抽出できなかった記事は、画像の部分を出さない（画像生成は ControlDeck の機能。ControlDeck で入・切できる）。
- ニュースハブと ControlDeck の設定は別々に持つ。ニュースハブは全部のデータを集め、ControlDeck は必要なデータだけを抽出する。
- Linux でも使えるように。まず Linux で開発してから、QNAP の QPKG として出力する。CI はなるべく使わず、ローカルの試験を前提に。開発の決まりは ControlDeck と同じ。
- OpenRouter の鍵は、ControlDeck と最初につないだときに ControlDeck から受け取りたい。難しければニュースハブの設定で入れる。

## 1. 全体の形

```
           ┌──────────────── QNAP ニュースハブ（24 時間）────────────────┐
RSS/Atom → │ 取得（間隔はソースごと） → 重複の除去 → 記事の DB（SQLite）      │
一覧の巡回 │   ├ 記事の画像（og:image・Google ニュースを元の記事に解く）     │
GitHub 等  │   ├ 下ごしらえ（無料の LLM、30 件ずつ、1 日の上限つき）         │
           │   ├ まとめ（日刊・週刊、無料の LLM。無ければ見出しの一覧）      │
           │   ├ 全文検索（SQLite FTS5）・チャンネル・アーカイブ             │
           │   └ 画面（放送局ほか・リーダー〔本文は元の記事へ〕）・取得先の管理 │
           │ 同期の API（ControlDeck 向け、前回からの分だけ）                 │
           └──────────────────────────────▲──────────────────────────────┘
                                          │ 電源を入れたとき・一定間隔で取りに行く
┌────────────── ControlDeck（サブ、電源を切ることがある）──────────────┐
│ ニュースハブから「必要な分」だけ受け取る（チャンネル・分野で絞る）         │
│ 重い処理: 本文の取り出しと訳（リーダー）・CPU の Gemma の下ごしらえ・      │
│           画像生成（CPU）・RAG・導入候補の検出・ゲームの見張り            │
│ ニュースハブが止まっているときだけ、自分で集める（今の取得の仕組み）        │
└──────────────────────────────────────────────────────────────────┘
```

- **取りこぼさない**: 多くの RSS は直近 10〜50 件しか出さない。電源の切れる ControlDeck では、記事の多いソース（GitHub・HN・ニュースサイト）が抜ける。24 時間のニュースハブが集める。
- **重い処理はしない**: QNAP は非力なので、LLM を動かさない・画像を作らない・埋め込み（RAG）を作らない。無料の外部 LLM を呼ぶだけ。

## 2. ニュースハブの中身

### 2.1 技術
- Python 3.12 ＋ FastAPI ＋ SQLite（WAL・FTS5）。画面は React ＋ Vite の静的な build（ControlDeck のニュースの画面を移植）。
- 依存は最小（httpx・feedparser 相当の自前の解析・Pydantic・FastAPI・uvicorn）。Trafilatura などの重い物は入れない（本文の取り出しは ControlDeck の役）。
- 1 プロセス（API・画面の配信・取得の見張り）。データの置き場は設定で変える（Linux は `~/.local/share/qnapnewshub`、QPKG は共有フォルダ）。

### 2.2 ControlDeck から移すもの（コードの元: `ControlDeck/backend/app/news/`）
| 機能 | 元 | ニュースハブでの扱い |
|---|---|---|
| ソース・目録・取得先ごとの間隔・一覧の巡回・通信確認・取得の履歴 | sources.py・catalog.json・probe.py・sourcemgr.py・fetchlog.py・feedgen.py | そのまま移す |
| 記事の DB・重複の除去・アーカイブ・全文検索 | db.py・store.py・fts.py | そのまま |
| 記事の画像（og:image）・Google ニュースを解く・ロゴの除外 | images.py・gnews.py | そのまま |
| チャンネル・好み・おすすめの順位・ホーム | channels.py・prefs.py・profile.py・home.py | そのまま |
| 下ごしらえ（無料の LLM） | prep.py・llm.py | 外部の LLM だけ（CPU の LLM の分は外す）。30 件ずつ（docs/research-free-llm-batch.md） |
| まとめ | digest.py | 外部の LLM だけ。無ければ見出しの一覧 |
| 画面（放送局ほか 5 デザイン・まとめのバブル・取得先の管理） | frontend/src/features/news・pages/News*.tsx | 移す。画像の無い記事は画像の部分を出さない |
| リーダー（本文の取り出しと訳） | reader.py | **移さない**。記事は元のページを開く（ControlDeck がつながっていれば ControlDeck のリーダーへのリンクも出す） |
| 画像生成・RAG・CPU の LLM | imagegen*・rag.py・cpu_llm.py | 移さない（ControlDeck の役） |

移したあとも ControlDeck と同じ作りを保つため、共通の部分は「ニュースの核」として同じ形のモジュールにし、片方を直したらもう片方にも当てる（いずれ共通の Python のパッケージに切り出すかを、移植のあとで判断する）。

### 2.3 認証
- 利用者のアカウント（最初の起動で管理者を作る。ログインは cookie の session）。
- ControlDeck の同期は、つないだときに発行する API トークン（取り消し可）。
- 既定で LAN の中だけで待ち受ける（0.0.0.0 にするかは設定。外に出すなら利用者の判断で、QNAP の逆プロキシと TLS を使う）。

### 2.4 無料の LLM の使い方
- 下ごしらえ: **30 件ずつ 1 回**。記事ごとに検査（JSON・番号・概要が日本語か）し、合わない記事だけ同じ回で 1 回送り直す。だめなら次の回、3 回で諦める（元の題と抜粋のまま）。
- 1 日の上限（既定 300 回）・1 分の上限（既定 10 回）。上限に近づいたら止めて次の日へ。混み合いは 20・60・120 秒待って最大 3 回。
- まとめ: 日刊・週刊で各 1 回。重点の指示・話題ごとの傾向・主な技術・注目点・3 行（ControlDeck と同じ）。
- 使った回数・失敗の理由を設定の画面に出す。
- 鍵は暗号化して保存（ニュースハブの置き場の鍵ファイルで。鍵の本文は画面・ログに出さない）。

### 2.5 実装で決めたこと（0.5 段・1 段。2026-11-24）
**モジュールの形**（`backend/qnapnewshub/`。ControlDeck の `app/news/` から移し、ControlDeck 側の依存を小さな置き換えに）:
- 核（ほぼそのまま）: `sources`（ソースの設定・整形・取得）・`catalog.json`・`presets`（目録）・`sourcemgr`（取得先の管理）・`fetchlog`（取得の履歴）・`feedgen`（フィードを作る手伝い）・`probe`（通信確認・サイトの発見・一覧の巡回・robots.txt）・`db`（SQLite・WAL）・`fts`（FTS5）・`store`（保存・重複の除去・アーカイブ・一覧・検索）・`images`（og:image・ロゴの除外）・`gnews`（Google ニュースを解く）・`channels`・`prefs`・`profile`（好み・おすすめの順位）・`home`・`topics`・`service`（取得の実行・見張り）。
- 外部の LLM: `llm`（OpenRouter の chat completions を httpx で直接。回数の上限・混み合いのやり直し・鍵）・`prep`（下ごしらえ）・`gist`（一言要約）・`digest`（日刊・週刊のまとめ）・`settings`。
- ニュースハブ側で新しく書いたもの: `config`（NEWSHUB_DATA・パスの検査）・`hubconf`（待ち受け）・`egress`・`net`（安全な取得）・`secretbox`（鍵の暗号化）・`auth`・`auth_router`・`router`（/api/v1/news）・`main`・`cli`。
- 移さなかったもの: reader（リーダー）・imagegen・rag・cpu_llm・ControlDeck の利用者 DB・通知・チャットの題（好みの `use_chat` は既定で切、ニュースハブには会話が無い）。出来事（kind=event）の記録は移さない（読む側の除外だけ残る）。
- 利用者の自分のリポジトリを隠す仕組み（`HIDDEN_SOURCE_PREFIXES`）は残し、既定は空（公開のリポジトリに利用者名を書かない）。既定のソースは `ggml-org/llama.cpp`・GIGAZINE・Phoronix・Hacker News・Hugging Face・2 つのフォーラム・r/LocalLLaMA（Reddit は鍵が無いので「取得しない」の注記になる）。

**データの置き場**（`NEWSHUB_DATA`、既定 `~/.local/share/qnapnewshub`。0700）: `news/news.sqlite3`（記事・操作・まとめ・取得の履歴）・`news/*.json`（ソース・チャンネル・好み・設定・`llm-calls.json`＝今日の回数）・`auth.sqlite3`（利用者・session・API トークン。ハッシュだけ）・`secrets.json`＋`secret.key`（暗号化した鍵と暗号化の鍵。0600）・`hub.json`（待ち受け）。

**外への取得**（AGENTS.md 7）: すべて `egress`（名前を解決 → 全アドレスが公開か検査 → 検査した IP へ接続。DNS rebinding 対策）。大きさの上限 5MB・時間の上限・リダイレクトは各段を検査（RSS の取得は追わない）・robots.txt を守る・ロボット確認はすり抜けない。

**LLM の使い方**（2.4 の実装）: 30 件ずつ。記事ごとの検査（JSON・番号・概要が日本語か。抜粋が空の記事は概要が空でよい）→ 合わない記事だけ同じ回で 1 回「必ず日本語で」を強めて送り直す → だめなら試行 +1・3 回で諦める。**送れなかった記事（鍵なし・上限・通信失敗）は試行を増やさず、次の取得で拾う**（直近 7 日・試行 3 回未満）。1 日の上限（既定 300 回、まとめ・一言要約も合計に数える）・1 分の上限（既定 10 回、超えそうなら空くまで待つ）・429 などは 20/60/120 秒で最大 3 回。設定の `GET /news/settings` の `llm_stats` に今日の回数（用途別）・失敗の数・直近の理由を出す。鍵が未設定なら下ごしらえ・まとめは「鍵が未設定」で止まる（取得・閲覧は動く。まとめは見出しの一覧にもせず、その回は作らない）。

**認証**: 最初の起動は利用者がいない。`POST /api/v1/auth/setup` か `./hub.sh create-admin` で最初の管理者（利用者がいる間は 409）。cookie の session（HttpOnly・SameSite=Lax・30 日）と ControlDeck 用の API トークン（`nhub_…`・読み取り専用・作った応答で 1 度だけ本体が見える・取り消せる）。書き込み・設定・鍵・トークンの管理は session の管理者だけ。cookie での書き込みは Origin が同じホストのときだけ。ログインの失敗は IP ごとに 5 分で 8 回まで。パスワードは scrypt。待ち受けは既定 127.0.0.1、`PUT /api/v1/auth/hub`（または `NEWSHUB_HOST`）で 0.0.0.0 にできる（再起動で効く）。

**API**（`/api/v1`。画面は 2 段）:
- 認証なし: `GET /health`・`GET /auth/status`・`POST /auth/setup`・`POST /auth/login`。
- 認証: `POST /auth/logout`、`GET|POST /auth/tokens`、`DELETE /auth/tokens/{id}`、`GET|PUT /auth/hub`。
- 読む（session か トークン）: `GET /news/items`・`archive`・`trends`・`profile`・`home`・`channels`・`prefs`・`export`・`settings`・`presets`・`digests`・`digests/{id}`・`sources`・`sources/manage`・`sources/manage/detail`。
- 書く（session のみ）: `POST /news/refresh`・`items/{id}/action`・`digests/run`・`sources/discover|check|generate|manage/bulk|manage/add`、`PUT /news/sources|channels|prefs|settings|profile/mute`、`GET|PUT|DELETE /news/openrouter-key`（鍵の本文は返さない。入っているかだけ）。
- ControlDeck の同期の API（`/sync/...`）・ペアリング・封じた鍵の受け取りは 4 段。

## 3. ControlDeck との受け渡し

### 3.1 つなぐ（ペアリング）
1. ニュースハブの設定に「ControlDeck とつなぐ」→ 6 桁のつなぐ番号（10 分有効）と、ニュースハブの公開鍵の指紋を表示。
2. ControlDeck の News の設定に「ニュースハブとつなぐ」→ ニュースハブの URL とつなぐ番号を入れる。ControlDeck は公開鍵の指紋を表示して、利用者がニュースハブの画面の指紋と同じかを確かめる。
3. ニュースハブが ControlDeck 用の API トークンを発行（ControlDeck は暗号化して保存）。

### 3.2 OpenRouter の鍵を渡す（できる。利用者の承認つき）
- つなぐ画面の「OpenRouter の鍵もニュースハブに渡す」（既定は切、押したときだけ）。
- **LAN の中でも鍵を平文で流さない**: ニュースハブの公開鍵（X25519）で ControlDeck が鍵を封じて（ECIES: X25519 ＋ HKDF ＋ AES-GCM。`cryptography` の部品で）送る。ニュースハブは自分の秘密鍵で開いて、置き場の鍵で暗号化して保存。公開鍵の指紋はつなぐときに利用者が目で確かめているので、途中のなりすましを防げる。
- 渡したことは両方の監査に残す。ニュースハブの設定で鍵を消す・入れ直すこともできる（鍵を手で入れる道も残す）。
- 渡すのは **鍵だけ**。ControlDeck の秘密の会話・特許・記憶などは何も渡さない（ニュースは公開の情報）。

### 3.3 同期の API（ニュースハブ → ControlDeck）
- `GET /api/v1/sync/items?cursor=<最後の番号>&limit=500&categories=…&channels=…` → 変化した記事（新規・下ごしらえの結果・画像の URL・ミュート）を、単調に増える変更番号の順に。ControlDeck は受け取った最後の番号を覚え、次はその続きから（電源を切っていた間の分も、ニュースハブに残っている限り取れる）。
- `GET /api/v1/sync/digests?since=…`、`GET /api/v1/sync/sources`（取得先の状態）、`GET /api/v1/health`。
- **ControlDeck が必要な分だけ**: ControlDeck の設定（受け取る分野・チャンネル・言語・期間）を問い合わせの絞り込みに入れる。ニュースハブは全部を持ち続ける。
- 受け取った記事は ControlDeck のニュースの DB に入れ、そこから先（リーダー・画像生成・RAG・導入候補の検出）は ControlDeck の処理。

### 3.4 ControlDeck の News の設定（機能の入・切）
- **データの出どころ**: ニュースハブ（既定、つないでいれば）／自分で集める。ニュースハブに一定時間つながらなければ自動で「自分で集める」に切り替え、つながったら戻る（画面に今どちらかを出す）。
- 機能の入・切: 自分での取得・下ごしらえ（CPU の Gemma）・**画像生成**・リーダー・まとめ・RAG への蓄積・導入候補の検出・ゲームの見張り。ニュースハブがやっていることは ControlDeck では切っておける（例: まとめはニュースハブのものを使う）。
- 受け取る範囲: 分野・チャンネル・言語・保存の期間。

## 4. 配布（Linux → QPKG）

**2026-11-24: QPKG を作った。作り方・入れ方・データの置き場・最初の管理者の一回限りの番号・確かめ方は `docs/QPKG.md`（こちらが正）。**
- まず Linux（Ubuntu・Debian）で: `pip install` か、自前の起動台本（venv を作る）で動かす。systemd のユーザーの単位も用意。

## 7. v0.1 の Write Coordinator・お休みモード・診断で、確かめたことと確かめていないこと（2026-11-24）

**確かめたこと（開発の PC・Linux・一時の置き場で）**
- 試験（`./hub.sh test`）: まとめ書き（間隔・件数・容量）・即時書きが書き手のスレッドを通ること・SIGTERM（実際の uvicorn の停止）で書き切ること・保存失敗でバッファを捨てないこと・未保存の `persisted:false` と差分が保存済みだけなこと・お休みの 3 つの動き（日をまたぐ時刻・休止が明けて保存）・休止中に DB・WAL・認証 DB の mtime と大きさが変わらないこと・診断に鍵・トークン・URL の問い合わせが出ないこと・診断が管理者だけなこと・systemd の単位の中身。
- E2E（320・1280、ライト・ダーク）: 診断の画面・自己点検・お休みの節（停電の説明つき）・ホームの一行の知らせ・☰ の「診断」。

## 8. v0.1 の取得のエンジン（条件付きの取得・Adaptive Polling・重複・CSV/OPML・出どころ）で、確かめたことと確かめていないこと（2026-11-24）
実装の細部と設計との違いは `ARCHITECTURE.md` 10 章の「実装と、設計と違った点」。

**確かめたこと（開発の PC・Linux）**
- 試験（`./hub.sh test`・新しい 44 件）: 304 で本文を解析しない・検証用の見出し（ETag・Last-Modified）が次の取得で送られる・解析に失敗した応答の ETag は覚えない・429 の Retry-After（秒・日時）・間隔の上下限（基準の 1/2〜8 倍）・出る間隔に合わせた間隔・バックオフ（2 倍・Retry-After・24 時間の上限）・固定・再起動後の続き・URL の正規化（追跡・AMP・http/https・末尾の /・www）・SimHash の近い重複（3 ビット以内）と窓（48 時間）・別の取得先だけまとめる・GUID・近い重複を保存して一覧は 1 件（`also`）・CSV の列の名前の揺れと文字コード（UTF-8・Shift_JIS）・OPML の入れ子と DTD の拒否・重複の数・書き出しの往復（CSV・OPML）・取り込みの API（そのまま追加は無効・通信確認は取れたものだけ）・出どころの推定と変更・診断の当たり率・古い DB への列と索引の追加。
- E2E（320・390・1280、ライト・ダーク。模擬の API）: 取り込みの確認の表（CSV・OPML）・そのまま追加・次の取得の予定といまの間隔（自動）・出どころの表示・固定と出どころの変更の送信。撮影は `frontend/test-results/shots/`。

**確かめていないこと**

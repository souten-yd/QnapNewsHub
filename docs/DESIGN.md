# QNAP ニュースハブ（QnapNewsHub）の設計

2026-11-24 利用者の決定（B 案）:
- 「QNAP ニュースハブと名前します」。ずっと電源の入っている QNAP（非力）で、ニュースを **集める・ためる・読む** を受け持つ。
- ControlDeck（メインの PC。電源を切ることがある）は **サブ**。必要なデータだけをニュースハブから抽出して使い、ニュースハブが止まっているときだけ自分で集める。ControlDeck のニュースの機能は最低限を持ち、機能の有効・無効を News の設定で変えられる。
- ニュースハブでも、ControlDeck と同じようなグラフィカルな画面でニュースを読める。画像が抽出できなかった記事は、画像の部分を出さない（画像生成は ControlDeck の機能。ControlDeck で入・切できる）。
- ニュースハブと ControlDeck の設定は別々に持つ。ニュースハブは全部のデータを集め、ControlDeck は必要なデータだけを抽出する。
- Linux でも使えるように。まず Linux で開発してから、QNAP の QPKG として出力する。CI はなるべく使わず、ローカルの試験を前提に。開発の決まりは ControlDeck と同じ。
- OpenRouter の鍵は、ControlDeck と最初につないだときに ControlDeck から受け取りたい。難しければニュースハブの設定で入れる。

## 1. 全体の形

```
           ┌──────────────── QNAP ニュースハブ（24 時間）────────────────┐
RSS/Atom → │ 取得（間隔はソースごと） → 重複の除去 → 記事の DB（SQLite）      │
一覧の巡回 │   ├ 記事の画像（og:image・Google ニュースを元の記事に解く）     │
GitHub 等  │   ├ 下ごしらえ（無料の LLM、20 件ずつ、1 日の上限つき）         │
           │   ├ まとめ（日刊・週刊、無料の LLM。無ければ見出しの一覧）      │
           │   ├ 全文検索（SQLite FTS5）・チャンネル・アーカイブ             │
           │   └ 画面（放送局ほか・リーダー〔本文は元の記事へ〕）・取得先の管理 │
           │ 同期の API（ControlDeck 向け、前回からの分だけ）                 │
           └──────────────────────────────▲──────────────────────────────┘
                                          │ 電源を入れたとき・一定間隔で取りに行く
┌────────────── ControlDeck（サブ、電源を切ることがある）──────────────┐
│ ニュースハブから「必要な分」だけ受け取る（チャンネル・分野で絞る）         │
│ 重い処理: 本文の取り出しと訳（リーダー）・CPU の Gemma の下ごしらえ・      │
│           画像生成（CPU）・RAG・導入候補の検出・ゲームの見張り            │
│ ニュースハブが止まっているときだけ、自分で集める（今の取得の仕組み）        │
└──────────────────────────────────────────────────────────────────┘
```

- **取りこぼさない**: 多くの RSS は直近 10〜50 件しか出さない。電源の切れる ControlDeck では、記事の多いソース（GitHub・HN・ニュースサイト）が抜ける。24 時間のニュースハブが集める。
- **重い処理はしない**: QNAP は非力なので、LLM を動かさない・画像を作らない・埋め込み（RAG）を作らない。無料の外部 LLM を呼ぶだけ。

## 2. ニュースハブの中身

### 2.1 技術
- Python 3.12 ＋ FastAPI ＋ SQLite（WAL・FTS5）。画面は React ＋ Vite の静的な build（ControlDeck のニュースの画面を移植）。
- 依存は最小（httpx・feedparser 相当の自前の解析・Pydantic・FastAPI・uvicorn）。Trafilatura などの重い物は入れない（本文の取り出しは ControlDeck の役）。
- 1 プロセス（API・画面の配信・取得の見張り）。データの置き場は設定で変える（Linux は `~/.local/share/qnapnewshub`、QPKG は共有フォルダ）。

### 2.2 ControlDeck から移すもの（コードの元: `ControlDeck/backend/app/news/`）
| 機能 | 元 | ニュースハブでの扱い |
|---|---|---|
| ソース・目録・取得先ごとの間隔・一覧の巡回・通信確認・取得の履歴 | sources.py・catalog.json・probe.py・sourcemgr.py・fetchlog.py・feedgen.py | そのまま移す |
| 記事の DB・重複の除去・アーカイブ・全文検索 | db.py・store.py・fts.py | そのまま |
| 記事の画像（og:image）・Google ニュースを解く・ロゴの除外 | images.py・gnews.py | そのまま |
| チャンネル・好み・おすすめの順位・ホーム | channels.py・prefs.py・profile.py・home.py | そのまま |
| 下ごしらえ（無料の LLM） | prep.py・llm.py | 外部の LLM だけ（CPU の LLM の分は外す）。30 件ずつ（docs/research-free-llm-batch.md） |
| まとめ | digest.py | 外部の LLM だけ。無ければ見出しの一覧 |
| 画面（放送局ほか 5 デザイン・まとめのバブル・取得先の管理） | frontend/src/features/news・pages/News*.tsx | 移す。画像の無い記事は画像の部分を出さない |
| リーダー（本文の取り出しと訳） | reader.py | **移さない**。記事は元のページを開く（ControlDeck がつながっていれば ControlDeck のリーダーへのリンクも出す） |
| 画像生成・RAG・CPU の LLM | imagegen*・rag.py・cpu_llm.py | 移さない（ControlDeck の役） |

移したあとも ControlDeck と同じ作りを保つため、共通の部分は「ニュースの核」として同じ形のモジュールにし、片方を直したらもう片方にも当てる（いずれ共通の Python のパッケージに切り出すかを、移植のあとで判断する）。

### 2.3 認証
- 利用者のアカウント（最初の起動で管理者を作る。ログインは cookie の session）。
- ControlDeck の同期は、つないだときに発行する API トークン（取り消し可）。
- 既定で LAN の中だけで待ち受ける（0.0.0.0 にするかは設定。外に出すなら利用者の判断で、QNAP の逆プロキシと TLS を使う）。

### 2.4 無料の LLM の使い方
- 下ごしらえ: **20 件ずつ 1 回**（2026-11-24 に 30 → 20。理由は research-free-llm-batch.md の追記）。記事ごとに検査（JSON・番号・概要が日本語か）し、合わない記事だけ同じ回で 1 回送り直す。だめなら次の回、3 回で諦める（元の題と抜粋のまま）。
- 1 日の上限（既定 800 回〔v0.2 で 300 から変更〕）・1 分の上限（既定 15 回）・用途ごとの割り当て（5.1）。上限に近づいたら止めて次の日へ。混み合いは 20・60・120 秒待って最大 3 回。
- まとめ: 日刊・週刊で各 1 回。重点の指示・話題ごとの傾向・主な技術・注目点・3 行（ControlDeck と同じ）。
- 使った回数・失敗の理由を設定の画面に出す。
- 鍵は暗号化して保存（ニュースハブの置き場の鍵ファイルで。鍵の本文は画面・ログに出さない）。

### 2.5 実装で決めたこと（0.5 段・1 段。2026-11-24）
**モジュールの形**（`backend/qnapnewshub/`。ControlDeck の `app/news/` から移し、ControlDeck 側の依存を小さな置き換えに）:
- 核（ほぼそのまま）: `sources`（ソースの設定・整形・取得）・`catalog.json`・`presets`（目録）・`sourcemgr`（取得先の管理）・`fetchlog`（取得の履歴）・`feedgen`（フィードを作る手伝い）・`probe`（通信確認・サイトの発見・一覧の巡回・robots.txt）・`db`（SQLite・WAL）・`fts`（FTS5）・`store`（保存・重複の除去・アーカイブ・一覧・検索）・`images`（og:image・ロゴの除外）・`gnews`（Google ニュースを解く）・`channels`・`prefs`・`profile`（好み・おすすめの順位）・`home`・`topics`・`service`（取得の実行・見張り）。
- 外部の LLM: `llm`（OpenRouter の chat completions を httpx で直接。回数の上限・混み合いのやり直し・鍵）・`prep`（下ごしらえ）・`gist`（一言要約）・`digest`（日刊・週刊のまとめ）・`settings`。
- ニュースハブ側で新しく書いたもの: `config`（NEWSHUB_DATA・パスの検査）・`hubconf`（待ち受け）・`egress`・`net`（安全な取得）・`secretbox`（鍵の暗号化）・`auth`・`auth_router`・`router`（/api/v1/news）・`main`・`cli`。
- 移さなかったもの: reader（リーダー）・imagegen・rag・cpu_llm・ControlDeck の利用者 DB・通知・チャットの題（好みの `use_chat` は既定で切、ニュースハブには会話が無い）。出来事（kind=event）の記録は移さない（読む側の除外だけ残る）。
- 利用者の自分のリポジトリを隠す仕組み（`HIDDEN_SOURCE_PREFIXES`）は残し、既定は空（公開のリポジトリに利用者名を書かない）。既定のソースは `ggml-org/llama.cpp`・GIGAZINE・Phoronix・Hacker News・Hugging Face・2 つのフォーラム・r/LocalLLaMA（Reddit は鍵が無いので「取得しない」の注記になる）。

**データの置き場**（`NEWSHUB_DATA`、既定 `~/.local/share/qnapnewshub`。0700）: `news/news.sqlite3`（記事・操作・まとめ・取得の履歴）・`news/*.json`（ソース・チャンネル・好み・設定・`llm-calls.json`＝今日の回数）・`auth.sqlite3`（利用者・session・API トークン。ハッシュだけ）・`secrets.json`＋`secret.key`（暗号化した鍵と暗号化の鍵。0600）・`hub.json`（待ち受け）。

**外への取得**（AGENTS.md 7）: すべて `egress`（名前を解決 → 全アドレスが公開か検査 → 検査した IP へ接続。DNS rebinding 対策）。大きさの上限 5MB・時間の上限・リダイレクトは各段を検査（RSS の取得は追わない）・robots.txt を守る・ロボット確認はすり抜けない。

**LLM の使い方**（2.4 の実装）: 20 件ずつ（2026-11-24 に 30 → 20）。記事ごとの検査（JSON・番号・概要が日本語か。抜粋が空の記事は概要が空でよい）→ 合わない記事だけ同じ回で 1 回「必ず日本語で」を強めて送り直す → だめなら試行 +1・3 回で諦める。**送れなかった記事（鍵なし・上限・通信失敗）は試行を増やさず、次の取得で拾う**（直近 7 日・試行 3 回未満）。1 日の上限（既定 300 回、まとめ・一言要約も合計に数える）・1 分の上限（既定 10 回、超えそうなら空くまで待つ）・429 などは 20/60/120 秒で最大 3 回。設定の `GET /news/settings` の `llm_stats` に今日の回数（用途別）・失敗の数・直近の理由を出す。鍵が未設定なら下ごしらえ・まとめは「鍵が未設定」で止まる（取得・閲覧は動く。まとめは見出しの一覧にもせず、その回は作らない）。

**認証**: 最初の起動は利用者がいない。`POST /api/v1/auth/setup` か `./hub.sh create-admin` で最初の管理者（利用者がいる間は 409）。cookie の session（HttpOnly・SameSite=Lax・30 日）と ControlDeck 用の API トークン（`nhub_…`・読み取り専用・作った応答で 1 度だけ本体が見える・取り消せる）。書き込み・設定・鍵・トークンの管理は session の管理者だけ。cookie での書き込みは Origin が同じホストのときだけ。ログインの失敗は IP ごとに 5 分で 8 回まで。パスワードは scrypt。待ち受けは既定 127.0.0.1、`PUT /api/v1/auth/hub`（または `NEWSHUB_HOST`）で 0.0.0.0 にできる（再起動で効く）。

**API**（`/api/v1`。画面は 2 段）:
- 認証なし: `GET /health`・`GET /auth/status`・`POST /auth/setup`・`POST /auth/login`。
- 認証: `POST /auth/logout`、`GET|POST /auth/tokens`、`DELETE /auth/tokens/{id}`、`GET|PUT /auth/hub`。
- 読む（session か トークン）: `GET /news/items`・`archive`・`trends`・`profile`・`home`・`channels`・`prefs`・`export`・`settings`・`presets`・`digests`・`digests/{id}`・`sources`・`sources/manage`・`sources/manage/detail`。
- 書く（session のみ）: `POST /news/refresh`・`items/{id}/action`・`digests/run`・`sources/discover|check|generate|manage/bulk|manage/add`、`PUT /news/sources|channels|prefs|settings|profile/mute`、`GET|PUT|DELETE /news/openrouter-key`（鍵の本文は返さない。入っているかだけ）。
- ControlDeck の同期の API（`/sync/...`）・ペアリング・封じた鍵の受け取りは 4 段。

## 3. ControlDeck との受け渡し

### 3.1 つなぐ（ペアリング）
1. ニュースハブの設定に「ControlDeck とつなぐ」→ 6 桁のつなぐ番号（10 分有効）と、ニュースハブの公開鍵の指紋を表示。
2. ControlDeck の News の設定に「ニュースハブとつなぐ」→ ニュースハブの URL とつなぐ番号を入れる。ControlDeck は公開鍵の指紋を表示して、利用者がニュースハブの画面の指紋と同じかを確かめる。
3. ニュースハブが ControlDeck 用の API トークンを発行（ControlDeck は暗号化して保存）。

### 3.2 OpenRouter の鍵を渡す（できる。利用者の承認つき）
- つなぐ画面の「OpenRouter の鍵もニュースハブに渡す」（既定は切、押したときだけ）。
- **LAN の中でも鍵を平文で流さない**: ニュースハブの公開鍵（X25519）で ControlDeck が鍵を封じて（ECIES: X25519 ＋ HKDF ＋ AES-GCM。`cryptography` の部品で）送る。ニュースハブは自分の秘密鍵で開いて、置き場の鍵で暗号化して保存。公開鍵の指紋はつなぐときに利用者が目で確かめているので、途中のなりすましを防げる。
- 渡したことは両方の監査に残す。ニュースハブの設定で鍵を消す・入れ直すこともできる（鍵を手で入れる道も残す）。
- 渡すのは **鍵だけ**。ControlDeck の秘密の会話・特許・記憶などは何も渡さない（ニュースは公開の情報）。

### 3.3 同期の API（ニュースハブ → ControlDeck）
- `GET /api/v1/sync/items?cursor=<最後の番号>&limit=500&categories=…&channels=…` → 変化した記事（新規・下ごしらえの結果・画像の URL・ミュート）を、単調に増える変更番号の順に。ControlDeck は受け取った最後の番号を覚え、次はその続きから（電源を切っていた間の分も、ニュースハブに残っている限り取れる）。
- `GET /api/v1/sync/digests?since=…`、`GET /api/v1/sync/sources`（取得先の状態）、`GET /api/v1/health`。
- **ControlDeck が必要な分だけ**: ControlDeck の設定（受け取る分野・チャンネル・言語・期間）を問い合わせの絞り込みに入れる。ニュースハブは全部を持ち続ける。
- 受け取った記事は ControlDeck のニュースの DB に入れ、そこから先（リーダー・画像生成・RAG・導入候補の検出）は ControlDeck の処理。

### 3.4 ControlDeck の News の設定（機能の入・切）
- **データの出どころ**: ニュースハブ（既定、つないでいれば）／自分で集める。ニュースハブに一定時間つながらなければ自動で「自分で集める」に切り替え、つながったら戻る（画面に今どちらかを出す）。
- 機能の入・切: 自分での取得・下ごしらえ（CPU の Gemma）・**画像生成**・リーダー・まとめ・RAG への蓄積・導入候補の検出・ゲームの見張り。ニュースハブがやっていることは ControlDeck では切っておける（例: まとめはニュースハブのものを使う）。
- 受け取る範囲: 分野・チャンネル・言語・保存の期間。

### 3 章の実装と、設計と違った点（v0.3 のニュースハブ側・feat/link-controldeck）
ControlDeck 側は別の PR。ここはニュースハブの API・画面・試験（`test_link.py`・`e2e/link.spec.ts`）。コードは `link.py`（つなぐ・鍵）・`changes.py`（差分）・`jobs.py`（仕事の列）・`artifacts.py`（画像・調査の記録）・`link_router.py`（API）。
- **つなぐ（3.1）**: `POST /api/v1/link/pairing`（管理者。6 桁の番号・10 分・指紋）→ ControlDeck が `POST /api/v1/link/pair`（番号・名前・自分の X25519 公開鍵〔base64 の 32 バイト〕。認証なし）→ **scope=link のトークン**と、ニュースハブの公開鍵・指紋が返る。番号は **メモリだけ**（再起動で消える。1 回だけ使える）。総当たり: 同じ番号への間違い 5 回でその番号は無効・同じ IP は 10 分に 8 回間違えると 429（正しい番号でも）。指紋は公開鍵の SHA-256 の先頭 80 ビットを 4 文字ごと（`1a2b-3c4d-5e6f-7a8b-9c0d`）。

- **鍵を封じて受け取る（3.2）**: `POST /link/secret`（link トークン）。ECIES の形は `link.py` の docstring が正（使い捨ての X25519 → ECDH → HKDF-SHA256〔salt = 使い捨て公開鍵 ‖ ニュースハブの公開鍵、info = `qnapnewshub-link-v1`〕→ AES-256-GCM、追加データ = `qnapnewshub-link-v1|<名前>`）。送る形は `{"v":1,"epk","n","c"}`（base64）。ControlDeck 側の実装の見本が `link.seal()`。ニュースハブの秘密鍵は secretbox（暗号化）の `link_x25519`。受け取れる名前は `openrouter` だけ（`llm.KEY_NAME` の枠へ）。名前と時刻と相手の名前だけを `link_secrets` に残し、値はログ・応答・診断・画面に出ない（試験で全部を grep）。改ざん・別の名前の枠への貼り替え・別の宛先向けは 422 で、保存済みの鍵は変わらない。
- **差分の同期（3.3）**: 設計の `GET /sync/items` ではなく **`GET /api/v1/changes?cursor=&limit=500&kinds=items,entities,events&channels=&categories=`**（ARCHITECTURE 5 章の API 表に合わせた）。変更番号は **DB の trigger**（`change_log`。物ごとに最新の 1 行・AUTOINCREMENT で単調）が付けるので、まとめ書き・取り出し・イベントの更新・古い記事の削除のどの経路でも漏れない。保存済みだけ（バッファは出ない）。op は upsert・delete・archive（`dup_of` で畳まれた記事）。削除の印は 90 日残す（まとめ書きの中で掃除）。前の版の DB を開いたときは、いまある物を全部「変更あり」として入れる。`reset: true` は cursor が最新より大きいとき。絞り込みで落ちた物も cursor は進む。**`/sync/digests`・`/sync/sources` は作っていない**（まとめ・取得先は既存の `/news/digests`・`/news/sources/manage` を読み取りトークンで読める）。

### 3.5 LAN での発見の応答（UDP。feat/lan-discovery・2026-11-25）
利用者「公開されている場合自動でアドレスを検知できないか？」（ControlDeck にハブの URL を入れ間違えた）。ControlDeck の「探す」が、LAN へ問いを送ってハブを見つける。コードは `discovery.py`・試験は `test_discovery.py`。
- **いつ答えるか**: 待ち受けが 127.0.0.1 以外（LAN に出している）のときだけ。127.0.0.1 では UDP の待ち受け自体を張らない。ポートは hub.json の `discovery_port`（既定 8788・0 で切。設定の「待ち受け」で変える・再起動で効く）か環境変数 `NEWSHUB_DISCOVERY_PORT`（数字か off）。張れなければ警告だけで API は動く。
- **問い**: `{"q":"qnapnewshub-discover","v":1}`（UTF-8 の JSON・256 バイトまで）。形が違えば何も返さない。
- **答え**: `{"q":"qnapnewshub-here","v":1,"name","version","urls":[…],"fingerprint"}`。urls は各インターフェースの IPv4（ループバック・リンクローカルを除く）× 待ち受けのポート。問いの送り元へ向かう道のアドレスを先頭に。fingerprint は link の X25519 公開鍵の指紋。トークン・番号・鍵の値・ユーザー名は入れない（試験で鍵の集合を固定）。
- **増幅の悪用への備え**: 答えは 512 バイトまで（urls 6 個まで）・全体で 1 秒に 5 通・同じ送り元から 1 秒に 1 通。超えた問いは黙って捨てる。問いが短く答えが長いので送り元を偽られると増幅になりうるが、倍率は 512 バイト／約 40 バイト以下に抑え、レートで総量を縛った。
- **受け取る側の決まり**（ControlDeck）: 答えの URL のうち、答えが来た送り元の IP と同じホストのものだけを採る。発見は情報だけで、つなぐには番号と指紋の見比べが要る（3.1 のまま）。
- **「つなぐ」の画面**: `GET /link` に `lan`（URL の候補・発見の応答の状態）を足し、ControlDeck の「ハブの URL」に写せる形で出す。
- **確かめていないこと**: 本物の LAN（複数のインターフェース・VLAN・QNAP の実機）でのブロードキャスト到達・QPKG でのポートの開放（QTS のファイアウォール）。

## 17. 検索の評価の物差し（`backend/tools/eval_retrieval/`・統合の段 I0 の前倒し・2026-11-25）

**目的は 1 つ**: LLM が引く検索の結果の精度と密度を、数字で比べられるようにする。以後の検索の変更（MPKR・翻訳・名寄せなど）は、この点数で良し悪しを決める（ControlDeck の PLAN-integrated-knowledge 6 章「良くなった所だけ既定にする」）。
実行: `./hub.sh eval-retrieval --data <評価用 DB の置き場（コピー）> --questions <json> --out <md> [--build] [--per-type 10] [--raw <json>]`。`--build` で問いの集めを作ってから流す。外へ通信しない・LLM は呼ばない。
**問いの集めと結果は利用者の実データ由来なので、リポジトリに入れない**（出力先は呼ぶ側が決める。基準値の記録は非公開の評価の置き場）。`--data` は**コピー**を渡す（流すとハブを起こすので、開いたときの更新が入る。既定の本物の置き場を指すと止まる）。

**問いの集め**（`build_questions.py`。DB を読むだけ・規則と雛形だけ・本物の LLM は使わない・同じ DB と seed なら同じ問い）。問いの文の自然さより、**正解の根拠が正しいこと**を優先する。正解は DB の構造から決める（public の物・文書だけ。名前が 2 文字以下・重複する名前の物は使わない）:
| 種類 | 雛形 | 正解の根拠 |
|---|---|---|
| 事実 | 「X は何を出したか」「X の価格は」「X のベンチマークは」 | その物の release／price／benchmark の主張（最大 4）・その根拠の文書・物 |
| 比較 | 「A と B の違いは」 | competes の関係・両方の物・関係の根拠の文書 |
| 変化 | 「A は B から何が変わったか」（replaces の関係）／「X の対応は最近どう変わったか」（日をまたぐ release の主張を 1 日 1 件ずつ） | 関係または主張・文書・物 |
| 複数の文書 | 「A と B をめぐる出来事は」 | 記事 3 件以上のイベントの主な物 2 つを**両方**含む記事（最大 5）・そのイベント・2 つの物 |
| 関係 | 「X を使っている／実装している／に対応している／の一部／を引用しているものは」 | その物を object にした関係の subject の物すべて・関係・根拠の文書・X |
| 日本語の問い・英語の記事 | 題がほぼ ASCII の記事に付いた日本語の主張を問いにする。半分は物の名前つき、半分は**名前なし**（日本語の文だけで英語の記事に届くか） | 英語の記事・主張・物 |
参照は `doc:<documents の id>`・`ent:`・`clm:`・`rel:`・`evt:`。問いの JSON は `{id, type, q, keywords, gold:{docs,entities,claims,relationships,events}, anchor}`。`keywords` は ①全文の検索語（LLM が打つ語の代わり）。

**測る道**（`runner.py`。既存の API を ASGI で直接呼ぶ。呼び出しごとにキャッシュを捨てる）:
① 全文だけ＝`GET /news/items?q=<keywords>`（今の検索）／② 種＝`POST /retrieve/seeds`（問いの文そのまま。文書・物・イベントを 1 件ずつ交互に並べる）／③ 種＋周り＝②の上位 3 つの物から `/graph/neighbors`（深さ 1）→ 辺・相手の物・辺の根拠の文書（`/retrieve/evidence`）を②と RRF（1/(10+順位)）で合わせる／④ 種＋局所 PPR＝`/graph/ppr`→ 上位の物・その主張と根拠の文書を②と RRF／⑤ 物の文脈＝③④を合わせ、上位 6 つの物の `/things/context`（text が LLM に渡る形・json から主張・関係・文書の参照を取る）。

**点数**（`metrics.py`・`report.py`）: 正解の根拠（上の 5 種類の参照）に対する **Recall@5・@10・@20・MRR・nDCG@10**（二値・問いごとに出してマクロ平均）・**文書だけ R@10**・参照の種類ごとの R@20・**文脈の密度**＝LLM に渡す文脈 1,000 トークンあたりに入っていた正解の根拠の数（①〜④は上位 10 件を 1 行ずつにした文、⑤は物の文脈＋上位 5 文書の題）・文脈に入った正解の割合・**時間 P50・P95**（その道に必要な呼び出しの合計）。すべて問いの種類ごとにも出る。トークンは見積り（ASCII 3.5 文字 ＝ 1、それ以外 1.3 文字 ＝ 1）で、道の比較のための相対の物差し。
**読み方の注意**（物差しの限界）:
- 正解は**厳密**（記されたものだけ）。同じ内容の別の記事は不正解として数える（精度は低めに出る）。文書の正解は 1〜5 件と少なく、文書だけの再現率は上限に近くなりやすい（差は物・主張・関係の再現率と、名前なしの日本語の問いに出る）。
- ①は文書しか返せないので、物・主張・関係を持つ正解の全体の再現率では不利になる。道の間の比較は「文書だけ R@10」と「参照の種類ごとの R@20」も見る。
- ⑤の並び（R@k・MRR）は、文脈から足した参照を RRF で混ぜるので薄まる。⑤は**文脈に入った正解の割合・密度・トークン数**で見る。
- 時間は ASGI の直呼びで、HTTP・TLS を含まない。QNAP では別に測る。LLM が計画する前後の検索の質（MPKR 本体）は、本物の MPKR が来てから I4 で同じ問いで測る。

**確かめたこと**: 試験 `tests/test_eval_retrieval.py`（8 件・小さな模擬のハブ）— 手で数えた Recall・MRR・nDCG・密度・百分位・トークンの見積り／RRF・交互の並べ方／問いの正解が DB の構造どおり（事実・比較・関係・変化・名前つきと名前なしの日本語・public だけ・2 文字以下の名前を除く・決定的）／5 つの道を通しで流せて表ができる／正解をそのまま並べると満点。評価用のハブのコピー（記事 2,540・物 3,803・主張 2,917・関係 397・イベント 148）で 60 問（6 種類 × 10）を約 10 秒で流せた。
**確かめていないこと**: 問い 60 問は小さい（種類ごと 10 問。差が小さい所は誤差）／問いは規則で作ったので、本物の利用者の問い（長い・曖昧・複数の意図）の分布ではない／意味（埋め込み）の検索・reranker・MMR・MPKR の計画は道に入っていない（I4・I8 で足す）／正解は LLM の取り出し（主張・関係）に依存し、その誤りは物差しに入る。

### 17.2 物差しの作り直しと、正解が消えた物を指す検査（fix/source-leak-yardstick・2026-11-26）
- **問いは DB が変わると古くなる**: 一般語の除外（retire）・名寄せ（merge）・型 other の関係の削除で、正解の物・関係・主張・イベントが DB から消える。消えた参照は取れないので、点数が実力より低く出て前後の比較を狂わせる（2026-11-25 の問いを翌日の DB で測ると、通常 60 問の 14 問・橋渡し 100 問の 80 問が消えた参照を指した）。
- **検査**（`tools/eval_retrieval/checks.py`）: 問いの正解の参照が今の DB（public）に在るかを確かめ、無ければ警告（stderr）。**作るとき**（`--build`・`--build-bridge` の直後）と**測るとき**（問いを読んだ直後）の両方で走る。数えるだけで問いは変えない（変えると前後の比較が崩れる）。警告が出たら問いを作り直す。
- **作り直しの手順**: 評価のハブの DB を SQLite の backup でコピー（本物へ書かない）→ コピーの上で夜の掃除（`kg_job.aggregate`）を 1 回流す → `--build`・`--build-bridge` → 測る。基準値は作り直した日の DB と問いの組に紐づく。前後の比較は同じコピー・同じ問いで行う。結果は評価の置き場（リポジトリに入れない）。

# QnapNewsHub — AI ニュース・ナレッジ分析基盤（設計 v2・2026-11-24）

利用者の構想（2026-11-24、「これをベースにしてさらにブラッシュアップして」）を土台に、それまでの設計（`DESIGN.md`・`KNOWLEDGE.md`・`research-free-llm-batch.md`）と実装（1 段: ニュースの核・認証・下ごしらえ）をまとめ直したもの。**この文書が正**。`DESIGN.md`・`KNOWLEDGE.md` は経緯として残す（食い違えばこちら）。

## 0. 目的
日々流れてくる情報を、**時間が経つほど価値が上がる知識のデータベース**に変える。記事を保存するだけでなく、記事に含まれる技術・事実・数値・ノウハウ・ほかの技術との関係を、独立したデータとして持つ。5 つの役割を 1 つにする。

| 役割 | 中身 |
|---|---|
| News Hub | 世界中のニュース・技術情報を集める（24 時間・取りこぼさない） |
| Knowledge Hub | 事実・技術・ノウハウを長くためる（根拠・時刻・履歴つき） |
| Intelligence Hub | トレンド・イベント・変化を見つける |
| Research Hub | ControlDeck の Web 調査と、ためた知識を一緒に使う。調査の結果もためる |
| Artifact Hub | AI 生成の画像・グラフ・報告を保管する |

## 1. 役割の分け方（変えない原則）
- **QNAP（TS-253Be 相当・Celeron J3455・x86_64・16GB）= 正本**: 集める・ためる・検索する・集計する・API。ControlDeck が止まっていても、単体で集める・ためる・全文検索・読む ができる。
- **QNAP の「無料の外部 LLM の係」= 文章の分析の主力**（2026-11-24 利用者「OpenRouter の無料 LLM を積極的に使い、QNAP 側で処理できると良い」）: QNAP は計算せず、OpenRouter の無料モデルを呼ぶだけなので非力な CPU でも回る。下ごしらえ（概要）・要素の取り出し（物・主張・数値）・イベントの代表の選び・まとめ（日刊・週刊）・知識カードの概要の書き直し・新着の傾向の解説を、ControlDeck が止まっていても QNAP だけで行う。
- **ControlDeck（R9700）= GPU と高品質の係**: 埋め込み（Embedding）・意味でのイベントのまとめ直し・詳しい分析・矛盾の検出・知識の統合・画像生成・報告。つながっている間に仕事を借りて、結果を返す。無料の LLM の結果の質の低いもの（検査に落ちたもの・重要度の高いイベント）を ControlDeck でやり直す。
- ControlDeck は NAS の SQLite を直接開かない。必ず API で（切断時の破損・競合を防ぐ）。
- ControlDeck の既存の機能・API を不用意に変えない（ControlDeck 側の変更は ControlDeck の決まりで PR を通す）。

## 2. 技術の選び方（利用者の案から変えた所と理由）
| 用途 | 採用 | 備考 |
|---|---|---|
| サーバー | **Python 3.12 ＋ FastAPI**（利用者の案は Go が第一候補） | ControlDeck とニュースの核を共有でき、1 段ですでに動いている。目標（常駐 512MB 以内・待機 CPU 1% 未満）を実機で測り、満たせない所だけ Go などに置き換える（v1.0 の前に判断）。 |
| 画面 | **React ＋ TypeScript**（案は Vue 3） | ControlDeck の画面（放送局ほか 5 デザイン・取得先の管理）をそのまま使い回せる。 |
| 記事・メタデータ・知識グラフ・ジョブ | SQLite（WAL・単一の書き手） | 1 つのファイルを正本に。大きくなったら年ごとのアーカイブ。 |
| 全文検索 | SQLite FTS5 ＋ **trigram**（日本語の部分一致） | 形態素解析（Sudachi）は ControlDeck の分析の仕事で行い、語の列を索引に足す（QNAP では辞書を常駐させない）。 |
| ベクトル | ControlDeck で計算 → **INT8 で QNAP に保存** | QNAP での意味の検索は測ってから（100 万件 × 384 次元 INT8 = 384MB、総当たりで 1 秒前後の見込み。足りなければ IVF の索引）。Qdrant は常駐させない（選べる道として残す）。 |
| 大量の集計 | 集計の表（増分）。必要なら DuckDB ＋ Parquet を夜に | 常駐の主データベースにはしない。 |
| 本文 | Zstandard で圧縮した塊（データベースの中の BLOB） | 細かいファイルを何百万も作らない。 |
| グラフ・チャート | Apache ECharts（遅延読み込み） | ヒートマップ・ツリーマップ・推移。 |
| 知識の地図 | Cytoscape.js（遅延読み込み） | 選んだ点の周りから段階的に広げる（一度に全部を送らない）。 |
| 配布 | QPKG（x86_64）・Linux・PWA | サーバーの起動時に npm build をしない（build 済みを配る）。 |

## 3. データの形
| 種類 | 中身 |
|---|---|
| Article | 個々の記事・論文・公式の発表（取得先・URL・GUID・題・抜粋・日時・言語・画像・本文の圧縮の塊・本文の hash） |
| Event | 複数の記事が報じる同じ出来事（代表の記事・関わる記事・一次情報かどうか・初報の時刻） |
| Entity | モデル・会社・人・製品・技術・制度など（正規化のキー・別名・種類・初出） |
| Claim | 記事が述べる個々の事実・主張（主語の物・内容・根拠の記事・確かさ〔公式／報道／実測の報告／未確認〕・時刻） |
| Knowledge | 再利用できる技術知識・ノウハウ（知識カード。AI の部分と利用者のメモの部分を分ける） |
| Relationship | 物・知識どうしの関係（種類〔使う・対応する・置き換える・競う・一緒に出る〕・根拠・確かさ） |
| Metric | 数値（性能・速度・価格・容量・金利）と **測定の条件**（モデル・量子化・GPU・VRAM・エンジン・版・文脈の長さ・同時数） |
| Note | 利用者のメモ・考察（**分析のやり直しで上書きしない**） |
| Trend | 話題の増減・新しい話題（日ごとの集計から） |
| Artifact | AI 生成の画像・グラフ・報告（hash で重複を管理、メタデータと置き場所） |
| Research | ControlDeck の調査（テーマ・検索の条件・見た出典・確かめた事実・比較表・その時の結論・分からない点・生成物） |

- すべての派生データに **根拠（記事・調査）・時刻・分析したモデル・分析の版・入力の版** を持つ。知識は上書きせず、**時系列の変化として残す**（例: あるモデルの ROCm の対応「非対応 → 実験的 → 正式 → 一部の環境で不具合」）。
- AI の回答そのものを事実として入れない。根拠を確かめられる情報だけを知識に統合する。

## 4. 1 日 1,000 件を知識に変える（段階的に）
| 処理 | 対象 | どこで |
|---|---|---|
| 取得（RSS・Atom・一覧の巡回・GitHub・arXiv など） | 全部 | QNAP |
| URL・GUID・hash の重複の判定、SimHash の近い重複 | 全部 | QNAP |
| 語の取り出し（統計・N-gram）・言語の判定 | 全部 | QNAP（軽い CPU の処理） |
| 本文の取り出し | 取れる記事（重要度の高い順・1 日の上限） | QNAP（Trafilatura。純 Python で軽い）／ControlDeck |
| イベントへのまとめ（粗く） | 全部 | QNAP（48 時間以内の記事で、SimHash・見出しの語・取り出した物の重なり） |
| 埋め込み・イベントのまとめ直し（意味で） | 重複を除いた記事 | ControlDeck（つながっている時） |
| 概要・要素の取り出し（物・主張・数値）を 1 回の呼び出しで | 全部（20 件ずつ。2026-11-24 に 30 → 20、理由は research-free-llm-batch.md の追記） | **QNAP の無料の外部 LLM**（落ちたものは ControlDeck の小さな LLM） |
| まとめ・知識カードの概要・新着の傾向の解説 | 変わった所だけ | **QNAP の無料の外部 LLM** |
| 詳しい分析・矛盾の検出・知識の統合 | 重要なイベント・新しい事実 | ControlDeck（高品質の LLM） |
| トレンド | 全部の統計 | QNAP（集計の表）・ControlDeck（トピックの分類） |

- 同じ出来事を 20 のサイトが報じても、詳しい分析は代表の 1 回。ほかの記事からは **新しい数値・異なる評価・追加の情報だけ** を取り出してイベントにまとめる。
- 優先度の低い記事も、検索できる状態で残す。
- 下ごしらえの件数: 無料の外部 LLM は 1 回 30 件（`research-free-llm-batch.md`）。ControlDeck の CPU の Gemma は 1 回 10 件。
- 1 日の分析の時間の目安（ControlDeck）: 簡易 200 件 × 300 トークン ＋ 詳細 50 件 × 1,000 トークン = 11 万トークン、40 tok/s で 0.8 時間（読み込み・埋め込み・載せ替えは別）。Radiance のように並列で伸びるエンジンでは、独立した記事の分析をまとめて流す。チャット・開発を優先し、ニュースの分析は低い優先度の裏の仕事。

### 4 章（イベント）の実装と、設計と違った点（v0.2 後半・2026-11-24）
`events.py`（まとめ・読み）・`event_llm.py`（要約）・`events_router.py`（`/api/v1/events`）。表は `events`・`event_articles`。
- **つなぐ条件**（2 記事が公開の時刻 48 時間以内で、どれか 1 つ。つないだ連結成分が 1 イベント。記事 2 件以上）: ①近い重複（dup_of か SimHash のハミング距離 3 以下。距離 3 は dedup.py の既存の値）②同じ言語で題の語の Jaccard 0.5 以上かつ共通 2 語以上 ③言語をまたぐ: 英数字の語（名前・版）の共通 2 語以上で、少ない方の 60% 以上 ④物の重なり（model/software/product/game/policy・数字を含む名前は重み 1、ほかは 0.5。合計 1.5 以上、題の語が 3 語以上重なれば 1.0 以上）。
- 一般的な語・物（前後 48 時間で 150 件より多い記事に出る）は手がかりにしない。1 イベントは 60 件まで（超えるつなぎは捨てる）。
- **増分と作り直し**: 関係が 2 記事だけで決まるので、まとめ書きの 1 トランザクションで新しい記事と物が付いた記事だけを見比べても、30 日分の作り直しと同じ分け方になる（試験で確認）。物の取り出しが後から付いた記事も、既存のイベントに加わる・イベントどうしが合わさる。
- **設計と違う点**: 埋め込み（意味でのまとめ直し）は v0.3（ControlDeck）で、QNAP の粗いまとめは語・SimHash・物だけ。1 記事だけのイベントは行にしない（「ほか N 件」の表示は 2 件以上のときだけ）。「独立したイベントの数」は分析の概要に、独立した記事数とは別の列で出す。
- **要約**: 記事 3 件以上・出どころ 2 以上のイベントだけ、10 イベントずつ 1 回の呼び出し（用途 `event`・既定 100 回。予備は 70 に減らし、card を 150 にして合計 800 に合わせた）。題・概要だけを材料に、記事の中の命令に従わない（枠で囲んだデータ・JSON だけ・道具なし）。**材料に無い数字を含む要約は捨て**、3 回で諦める。古い設定の保存済みの割り当ては、event を足して予備から引く形で移行する。

## 5. 仕事の列（ジョブ）と ControlDeck の受け渡し
- QNAP が仕事を持つ: 種類（本文・埋め込み・まとめ・要約・取り出し・詳細・統合・画像）・入力の版・**重複を防ぐ ID**・**期限つきの借り（lease）**・やり直しの回数・使ったモデル・状態。
- 係（worker）が借りて返す:
  - **ControlDeck**（つながっている間。GPU・CPU）
  - **QNAP の中の「無料の外部 LLM の係」**（既定で入。文章の仕事は常にこちらが先に借りる。ControlDeck は GPU の仕事と、やり直し・高品質の仕事を借りる）
  - **QNAP の上で LLM を動かすことは、既定で切**（非力なため）。
- ControlDeck が途中で止まっても、借りの期限が切れた仕事は列に戻り、再開後に安全に続く。同じ入力の版の結果は二重に入らない。

### つなぐ・鍵を渡す
- 6 桁の番号 ＋ ニュースハブの公開鍵の指紋（利用者が両方の画面で見比べる）でトークンを発行。

### 無料の外部 LLM を積極的に使う（5.1）
- **予算**: アカウントの無料モデルの上限は 1 日 1,000 回（課金の残高があるため。無いと 50 回）。ニュースハブの既定は **1 日 800 回・1 分 15 回**（ControlDeck のほかの用途に残す。設定で変える）。用途ごとの割り当て（既定）: 下ごしらえと取り出し 300・本文の取り出しの後の要約 150・まとめ 20・知識カード 200・傾向の解説 10・予備 120。余った枠は夜に後回しの仕事（古い記事の取り出し直し・カードの書き直し）へ回す。1 日 1,000 記事でも下ごしらえは約 35 回で済む。
- **モデルの順番と切り替え**: 既定は Nemotron 3.5 Super（無料）、次に設定で並べた無料モデル。429・空の答え・検査落ちが続いたら次のモデルへ（20/60/120 秒の待ちの後）。モデルごとの成功率・日本語の率・速さを記録し、診断に出す。有料モデルも設定で選べる（使った額を表示）。
- **質の守り**: JSON Schema・番号・日本語の率・原文に無い数値の検出（取り出した数値は原文に同じ数字があるものだけ）・記事ごとの送り直し 1 回・3 回で諦めて ControlDeck のやり直しの列へ。AI の出力は「AI の取り出し（無料モデル名・版）」の印つきで、確かめた事実とは分ける。
- **守り**: 記事の中の命令に従わない（system に明記・出力は JSON だけ・道具は渡さない）。秘密の情報は送らない（ニュースハブにあるのは公開の記事だけ）。

### 5.1 の実装と、設計と違った点（v0.2 前半・2026-11-24）
`llm.py`（予算・割り当て・ゲートウェイ）・`llm_models.py`（順番と切り替え）・`prep.py`（取り出しを同じ呼び出しで・夜の後回し）・`extract.py`（検査）・`entities.py`（保存と読み）・`entities_router.py`・`llm_try.py`。
- **予算**: 既定 1 日 800 回・1 分 15 回。用途は `prep`（下ごしらえと取り出し 300）・`gist`（要約 150）・`digest`（まとめ 20）・`card`（知識カード 200）・`trend`（傾向の解説 10）・`spare`（予備 120）。設定 `llm.quota`。合計が上限を超える保存は 422（黙って縮めない。割り当てを書かない古い設定は、既定の割合を上限に合わせて縮める）。自分の割り当てを使い切った用途は予備から借り、予備も尽きたら `LlmQuotaLimit`（LlmDailyLimit の一種。呼び出し側は「後で」）。`card`・`trend` は枠だけで、呼ぶ処理は v0.5 以降。
- **夜の後回し**: `backfill`（取り出しが済んでいない古い記事〔14 日以内・`extract_v=0`〕の取り出し直し）。night_from 時（既定 21）以降、その日の使い残した割り当て（予備の残りを含む）の合計まで。概要は作り直さない。1 回の取得につき最大 300 件。
- **設計と違う点**: 使い残しの計算は「夜の時点の残り」で、日付をまたぐ（0〜6 時）と新しい日の枠になる。上限が 1 日の合計に掛かるので、夜に使いすぎて翌朝のまとめが止まることは無い。「本文の取り出しの後の要約」は gist の枠（一言要約）に当てた。
- **モデルの順番**: `prep_model`（1 番目）＋`fallback_models`（最大 4）＋ゲートウェイ。直近 5 回で 3 回失敗（429・空の答え・通信の失敗・検査落ち）で次へ、30 分で 1 番目へ戻る。失敗の記録は llm.py（HTTP・空）と prep.py（検査）の 2 か所だけ、成功は prep.py だけ。待ちの途中で切り替われば、20/60/120 秒の待ちを飛ばして次のモデルで同じ回を続ける。メモリだけで持ち、モデルごとの 1 日の要約だけ日が変わったとき `news/llm-models-daily.json`（30 日分）に 1 回書く。**まとめ・一言要約は順番に乗せず、それぞれ固定のモデル**（v0.2 の後半で乗せる）。
- **ゲートウェイ（利用者の追加の要望）**: 行き先は OpenRouter と ControlDeck のゲートウェイ（OpenAI 互換。モデル名は内部で `gateway:<名前>`）。設定 `llm.gateway`（URL・モデル・先にするか・1 回の件数 既定 10・時間切れ 既定 300 秒・1 分の上限 既定 6・飛ばす分 既定 10）と鍵（暗号化）。ゲートウェイには 1 日の上限・割り当てを掛けず、1 分の上限と同時 1 本だけ。接続できない・時間切れ・5xx で順番から外し（冷却）、冷却が明ければまた試す。4xx は「つながらない」とはせず失敗として数える。URL は設定の値だけ（LAN の私的な IP を許す。egress の守りとは別の道で、記事の中の URL からは呼ばない）。診断の束には URL を書き出さない。**設計との違い**: 順番の各行を「行き先＋モデル」の自由な並びにはせず、OpenRouter の並び（prep_model＋fallback_models）の前か後ろにゲートウェイを 1 つ置く形にした（`first`）。
- **取り出し**: 下ごしらえと同じ 1 回の呼び出し。JSON Schema の部分集合の自前の検査（`extract.validate`。依存を増やさないため jsonschema は使わない）で 1 件ずつ検査し、合わない物・fact だけ捨てる（記事は落とさない）。fact の数字は題と抜粋（送った 400 文字まで）にあるものだけ。漢数字・単位の言い換えは照合できないので捨てる（安全側）。取り出しが無い・形が違う記事は `extract_v=0` のままで、夜に拾う。
- **保存**: `entities`（key は NFKC・小文字・文字と数字だけ。1 つの key は 1 行。種類は最初のもの、`other` だけ後で具体的な種類へ）・`entity_aliases`・`article_entities`・`claims`（`ai_extracted`・モデル名・`prompt_version`）。`news_items.extract_v` を追加。**設計と違う点**: 種類が違っても key が同じなら同じ物（LLM が Qwen を model と org で揺らしても割れない代わりに、同名の別物は 1 つになる）。`source_article_id` はいまは取り出した記事と同じ（重複の代表へ寄せるのは後の段）。`article_count` は取り出しのたびに数え直すが、古い記事の削除（prune）では数え直さない（次にその物が出たとき直る）。まとめ書きに乗せた（`writer.stage_extraction`。同じ 1 トランザクション）。未保存の取り出しは API に出ない（保存のあとに出る）。
- **API**: `GET /entities`（q・type・days・sort・limit・offset）・`GET /entities/{id}`（年表 100 件・facts 200 件・一緒に出る物の上位 10）。ニュースの一覧の各記事に `entities`（最大 4 の札）。

### 5 の実装と、設計と違った点（v0.3 のニュースハブ側・2026-11-24）
`jobs.py`・`changes.py`・`artifacts.py`・`link.py`・`link_router.py`。ControlDeck 側（係）は別の PR。
- **表 jobs**: 種類 `embed`・`event_merge`・`summarize_hq`・`extract_retry`・`image`（設計の「本文・まとめ・詳細・統合」は、作り手のある 3 つ＋取り込み口だけの 2 つにした）・入力の版（`input_v`）・重複を防ぐ ID（`dedup_key = 種類:対象:入力の版`・UNIQUE）・lease_until・試行（借りるたび +1。上限 3 で dead）・状態（queued・leased・done・dead）・使ったモデル。
- **API**: `POST /jobs/claim`（種類・件数〔最大 50〕・lease 秒〔30〜3600、既定 300〕）・`POST /jobs/complete`（`results` の配列。1 回 50 件まで。各件 done／failed）。complete の状態は done・duplicate（2 回目。何も変えない）・rejected（検査に落ちた。列に戻る）・failed・dead・unknown・lease_conflict（別の係の生きた借り）。**期限切れは claim のとき（と診断の読みで「期限切れ」として数える）列に戻る**＝ControlDeck が来ない間は何も書かない。期限が切れた後の遅れた結果も、誰も終えていなければ受け取る。
- **仕事の作り手は claim のときに作る**（設計の「作り手」を常駐の処理にしなかった。書き込みを増やさず、ControlDeck が要る種類だけ）: `extract_retry` = 下ごしらえが済んだ（または 3 回で諦めた）のに取り出しが空の記事（14 日以内）・`summarize_hq` = 出どころ 3 以上のイベント・`image` = 出どころ 3 以上のイベントの代表の記事で画像が無いもの。1 回の claim で種類ごとに最大 100 件を作る。`embed`・`event_merge` の作り手は v0.6 以降（取り込み口だけ）。
- **結果の取り込み（検査してから）**: `extract_retry` は `extract.clean`（JSON Schema の部分集合＋数字が原文にあること）→ `stage_extraction`（まとめ書き）→ 保存してから done。`summarize_hq` は 20〜1500 文字・`stage_event_summary`。`embed` は model・dim（8〜8192）・scale・dim バイトの INT8（表 `embeddings`。本体は jobs.result に残さない。使う検索は v0.6）。`image` は `PUT /artifacts` で送った画像が記事に付いていること（sha256 の一致）を確かめるだけ。`event_merge` は groups の形だけ検査して残す（イベントのまとめ直しへの取り込みは v0.5 以降）。結果の大きさは 200,000 文字まで。
- **生成物**: `PUT /artifacts/items/{id}/image`（本文は画像。webp・png・jpeg・512KB まで・申告より多く送られても上限で止める）。構造を最後まで見る（PNG は chunk の長さ・CRC・IDAT・IEND、JPEG は SOI/EOI と SOF の寸法、WebP は RIFF の長さと寸法）・幅と高さ 64〜4096。デコードはしない（依存を増やさない）。sha256 が名前（`data_dir/artifacts/images/<sha256>.<ext>`・表 `artifacts`）で、同じ中身は 1 つ。記事の `image_url` を内部の道（`/api/v1/artifacts/images/…`・認証つき）に、`news_items.image_ai=1`（画面に「AI 生成のイメージ」）。元の画像（AI 生成でない）があれば 409（`replace=true` で上書き）。**差し替えは保存（flush）してから返す**。`POST /research`（テーマ・出典〔http(s)〕・確かめた事実・結論。大きさを制限・内容の sha256 で二重に入れない。保存だけ）。
- **設計との違い**: `/knowledge/batch`・`POST /artifacts`（報告の保管）・`GET /storage/status` は未実装（v0.5・v0.8）。ControlDeck の中の係（本文・要約・取り出し・イベントの実行）は ControlDeck の PR。画像の「重要」の基準は出どころ 3 以上のイベントの代表だけ（利用者の好み・ホットトピックとの組み合わせは後で）。

## 6. 知識（Obsidian を発展させたもの）
- **知識カード**: 概要・技術の要素・用途・制約・関連の実装・条件別のベンチマーク・変化の履歴・根拠の論文と記事・**自分のメモ**（AI の部分と分けて、再分析で上書きしない）。
- **地図**: 点を押すと、関係する記事・性能の測定・関連の技術・過去の変化・公式の情報・未解決の問題・利用者のメモ。バックリンク。自動の関係は確かさと根拠つき（根拠の無い関係は確定として入れない）。
- **更新の履歴と矛盾**: 時点ごとの状態と根拠を残し、「過去 3 か月で AMD GPU 向けの推論はどう進んだか」「以前は非対応で最近対応したモデル」「公式と実測で評価の違うもの」に答えられるように。

### 3・6 章の実装と、設計と違った点（v0.5 知識グラフ・2026-11-25）
`kg.py`（文書・根拠・関係・機密の区分・履歴と矛盾・co_occurs）・`kg_view.py`（カード・neighbors・書き出し）・`kg_job.py`（夜の集計とカードの概要）・`kg_router.py`（`/kg`・`/graph`）。統合ナレッジ基盤の土台（ControlDeck の `docs/PLAN-integrated-knowledge.md` 4 章）として、ニュース専用にしていない。
- **表**: `documents`（種類 news・paper・repo・model・research・note・patent・standard・other／正規化した識別子 `url:`・`doi:`・`arxiv:`・`repo:github.com/owner/name@sha`・`patent:`・`standard:`／sensitivity public・confidential／ai_use allowed・local_only・prohibited／出どころ・日時・版）・`evidences`（文書・主張か関係・文字の範囲 start〜end・ページ・短い引用・その sha256・原文に照合できたか・確かさ。**1 つの主張・関係が根拠を複数持てる**）・`relationships`（主語・目的語・型・向き・確かさ・状態・根拠の数・最初と最後の日時・生成した活動〔model・版・人〕・区分）・`entity_notes`（利用者のメモ）・`entity_cards`（AI の概要）。
- **ニュースの記事は `news_documents`（対応の表）で documents へ結ぶ**（設計は「ビューか対応の表」。列を足さず、既存の `news_items` は無変更）。`sync_documents` は冪等（`INSERT OR IGNORE`・前回の続きの印 `kg_doc_hi`・抜けの点検は `full`）。同じ正規化 URL の記事は同じ文書を指す。取り出しの保存（`apply_extractions`）の中で、その記事の対応を必ず作ってから主張・関係を入れる。
- **`claims` は既存の表を使い、`article_id` を NULL 可にした**（記事の無い文書の主張のため）。SQLite は列の制約を変えられないので、古い形のファイルを開いたとき 1 回だけ表を作り直して行を写す（`db._rebuild_claims`。2 回目以降は何もしない）。`document_id`・`sensitivity`・`ai_use` を足した。主張の根拠は evidences（ニュースの主張は文書だけで、位置・引用は持たない。取り出しの入力に位置が無いため。**根拠を作っていない**）。
- **機密の区分の引き継ぎ**（`kg.inherit`）: 派生データ（主張・関係・物）の区分は、根拠の文書のうち最も厳しいもの。文書の既定は fail-closed（confidential・local_only）で、ニュースだけが public・allowed。既にある文書の区分は厳しい方へしか動かない。関係の根拠に機密の文書が 1 つでも混ざれば、その関係は機密。物は、公開の記事に出たことがあれば public のまま、機密の文書だけから作られた物は confidential。**読む API の既定は public だけ**で、`confidential=true` はログインした管理者だけ（API トークン〔読み取り・つないだ ControlDeck〕は 403）。メモの書き出しもログインだけ。**カードの概要の LLM は public かつ allowed の物・主張だけを送る**（試験で、機密の物の名前・主張が送られないことを確かめた）。
- **関係の型と確かさ**: 型は uses・supports・replaces・competes・part_of・implements・cites・contradicts・co_occurs・other。向きの無い型（co_occurs・competes・contradicts）は `subject_id < object_id` にそろえる。状態は `extracted`（引用が原文にある AI の取り出し。確かさ 0.7、別の文書でも出るたびに +0.1・上限 0.9）・`inferred`（**推測**。引用が無い・原文に無い。確かさは 0.35 を超えない）・`statistical`（一緒に出る集計）・`confirmed`（人が API で根拠〔引用〕つきで入れたものだけ）。**自動では確定を作らない**。
- **LLM の型つきの関係（`relations`）**: 下ごしらえと同じ 1 回の呼び出し（呼び出しは増えない・件数 20 のまま）の返事に、記事ごとに最大 5 件。subject・object は物の名前、quote は題か抜粋から写した 60 文字以内の引用。`extract.clean_relations` が 1 件ずつ検査する（型・同じ物どうし・重複・6 件目以降を捨てる。引用が原文〔NFKC・空白を除いて〕にそのままあれば grounded）。プロンプトの版を `ex1` → `ex2`、`TOKENS_PER_ITEM` を 500 → 600 にした（20 件で出力の上限 12,000 ちょうど。出力の見積もりは DESIGN 13 章）。再取り出しのとき、その記事の AI の関係の根拠だけを消して入れ直し、根拠が 0 になった関係は消える（人が入れた根拠・関係は残す）。
- **co_occurs は集計**（`rebuild_cooccur`・LLM なし・夜に 1 日 1 回）: 「単位」＝同じイベントの記事は 1 つ・イベント外の記事は 1 記事で 1 つ（重複〔`dup_of`〕は数えない）・直近 180 日。回数 3 以上かつ期待値の比（c × 全単位数 ÷ (df_a × df_b)）2 以上の組だけ。作り直しは置き換え（行の id は安定しない。co_occurs に根拠の行〔evidences〕は作らず、書き出しのときに共通の記事を 3 件まで引く）。
- **履歴と矛盾は読むときに計算する**（`kg.history`・保存しない・上書きも削除もしない）。value を持つ主張だけを、同じ物・同じ種類（release・price…）で時系列に並べる: 時間を置いて値が変われば `change`（前の値つき）、`CONTRADICT_DAYS`（3 日）以内に別の文書が別の値を述べれば `contradiction`（双方に印）。**value の無い主張（文章だけの対応状況など）は比べない**（設計の「対応状況」の一部は、取り出しが値を返したときだけ）。
- **知識カード**: 概要（夜〔`night_from` 以降〕に 10 物ずつ・用途 `card`〔既定 150 回〕・変化のあった物だけ〔材料の指紋 sig が変わったとき。記事の数は桁だけ見る〕・記事 3 件以上で主張か関係のある物・数字が材料に無い概要は捨てる・同じ材料で 3 回失敗したら諦める・古い概要は残す）・要素（別名・初出と最後・記事の数・話題の語）・年表・主張と根拠・関係・変化と矛盾・利用者のメモ。**メモは別の表に即時保存**（`PUT /kg/entities/{id}/note`。書き手の 1 トランザクション）。再分析・概要の作り直しは触れない。
- **地図**: `POST /api/v1/graph/neighbors`（物の id 最大 50・辺の型・深さ 1〜3〔既定 1〕・limit 最大 1,000〔既定 200〕・確かさ・物の種類・期間）は、段ごとに 1 回のまとめ取り（`IN`）で、確かさの高い順に上限まで返し、`truncated` を付ける。`GET /graph/seeds` が入り口の候補。画面は Cytoscape.js 3.33.1（地図を開いたときに遅延読み込み）。**点を押すと札が出て、そこから「知識カードを開く」「この物の周りを広げる」**（押しただけでカードへ飛ぶと、広げられないため）。型・確かさ・期間・種類の絞り込みは読み込み済みの線を隠し、次に広げるときの条件にもなる。推測・集計の線は破線。
- **Obsidian の書き出し**: `POST /kg/export`（物の id か、種類・期間・記事数の条件。最大 2,000 物）。物ごとに `<種類>/<名前>.md`（YAML の front matter〔id・name・type・aliases・first_seen・last_seen・article_count・sensitivity・ai_use・exported_at〕・概要・`[[関係する物]]`〔確かさ・状態・根拠の数〕・変化と矛盾・主張と根拠〔URL・引用・ページ〕・自分のメモ）を zip にして返す。押したときだけ。区分の既定は public だけ。範囲外の物へのリンクは出さない。
- **まだ無いもの**: ニュース以外の取り込み（統合の段）・物の統合（同じ物の別名寄せ。今は正規化のキーだけ）・`cites` を本文から取る処理・ニュースの主張の根拠の位置（文字の範囲）・局所 PageRank と `/research`（v0.6）。

## 7.5 新着の傾向（2026-11-24 利用者「新規記事の傾向」）
- 取った新しい記事の傾向を、時間ごと・日ごとに見る: 件数（分類・チャンネル・取得先・言語）・新しく出た物と語・急に増えた語・重複の率（同じ出来事の報道の数）・画像のある率・遅れ（発表から取得まで）・一次情報の率・止まった取得先の影響。
- 画面「新着の傾向」: 直近 24 時間と前の 7 日の平均の比較・時間ごとの積み上げ・新しく出た物の一覧・分野ごとの勢い。数字はすべて集計の表から（LLM なし）。
- 無料の LLM が 1 日 1〜2 回、数字と新しく出た物を材料に「今日の傾向」を数行で解説（根拠の数字と記事へのリンクつき）。

### 7・7.5 の実装と、設計と違った点（分析の第 1 版・2026-11-24）

## 8. 検索と調査（ControlDeck との統合・優先度が高い）
- ControlDeck の Web 検索に、ニュースハブを追加の検索の提供元として入れる。ハイブリッド（全文・意味・物・つながり・時系列・数値・Web）を RRF で合わせ、必要なら reranker で並べ直す。LLM には関係の強い記事・知識カード・事実・数値だけを渡す。
- 調査の記録（テーマ・条件・出典・確かめた事実・比較表・結論・分からない点・生成物）をニュースハブへ送り、次の調査では前回からの変化を中心に調べる。
- 秘密の会話・特許の流れからの調査は送らない（ControlDeck の守りの規則のまま）。

### 8 章（検索）・3 章（本文）・9 章（圧縮）の実装と、設計と違った点（v0.2 後半・2026-11-24）
`backend/qnapnewshub/searchindex.py`（索引）・`bodies.py`（本文の取り出し）・`ztext.py`（Zstandard）・`maintenance.py`（作り直し・圧縮・本文の 1 分ごとの巡回）。
- **索引は 2 つ**（FTS5・中身を持たない表 `content='' contentless_delete=1`）: `news_fts_tri`（trigram。日本語の部分一致）と `news_fts_word`（`porter unicode61`。英語の語幹）。列は 題・概要（日本語）・物の名前・抜粋・出どころ。BM25 の重みは 題 6・物 3・概要 2・抜粋 1・出どころ 1。
  **設計の「今の FTS5 に trigram を足す」は、「今の索引（題・抜粋・出どころの 3 列の外部コンテンツ・trigram）を、5 列の中身なしの 2 つに置き換える」になった**（物の名前の列が要るため。外部コンテンツ表は存在しない列を持てない）。
- **語の振り分け**: ASCII の語 → 英語の索引（語幹で一致。1 件も無く、全部が 3 文字以上なら trigram の部分一致に落とす）／ASCII 以外で 3 文字以上 → trigram／それ以外（2 文字以下の日本語など）→ LIKE（題・概要・抜粋・出どころ）。両方の索引の語があれば 2 つの表を rowid で結び、BM25 を足す。
  語はすべて含む（AND）。**RRF ではなく BM25 の和**（2 つの表が同じ記事を指すとき、足すのが素直で、片方だけの記事は混ぜる必要が無いため。RRF は v0.6 の「意味の検索との合成」の所で使う）。
- **順位づけの候補は上位 600 件**。そこから「見える記事・種類・出どころ・話題・日付・ミュート」の条件で絞り、`o:<位置>` でページを送る（600 件より先は見えない。検索語を足して絞る使い方）。新しい順の検索は、検索語が無いときだけ。まだ書いていない記事（未保存）は先頭に出す（Python の部分一致）。
- **索引の更新は news_items のトリガー**（挿入・題／抜粋／概要／出どころの更新・削除。`image_tried` などの更新では動かない）。トリガーが動くのはまとめ書きのトランザクションの中だけなので、「書き込みはまとめ書きだけ」は守られる。物の名前は `entities.apply_extractions` が同じトランザクションで入れ直す。
  **古い DB**（v0.1・外部コンテンツの索引）は、開くとき古い表・トリガーを消して新しいものを作り（以後の書き込みは索引に載る）、既存の行の分は `maintenance.index_step` が 1 バッチ 2 万件・1 トランザクションで入れる（1 分ごと。お休み中は進めない。WAL が 32MB を超えたら checkpoint）。
  入れ終わるまでの検索は、未索引の範囲を LIKE で補う（遅いが、見つからないことは無い）。診断の「検索の索引を作り直す」（`POST /diagnostics/search/rebuild`）で全件の作り直しを予約できる。
- **本文の取り出し（3 章の Article の本文・8 章）**: 記事のページを `net.get`（SSRF の守り・大きさ 2MB・時間 15 秒・リダイレクトは各段で robots を確かめる）で取り、Trafilatura（`favor_precision`・コメントと表は入れない）で本文を取り出して Zstandard（level 9）で圧縮し、`news_body`（BLOB）へ。
  **本文は索引に入れない**（設計の「抜粋・本文の索引」は、題・概要・物・抜粋だけにした。本文を trigram に入れると索引が数倍になるため）。本文の使い道は ①下ごしらえ（LLM）の入力（抜粋の代わりに本文の頭 1,500 文字） ②「本文あり」の印 ③v0.3 以降の ControlDeck への受け渡し。
  対象は直近 14 日の新着の `kind=news` の代表の記事。重要度は 近い重複の数 × 3 ＋ 取り出した物の数 ＋ 新しさ（0〜2）。上限は 1 日 200 件（試行は失敗も数える）・1 分 6 件（1 分ごとの巡回が 1 回に取る件数）・同じホストへは 3 秒あける。
  守ること: robots.txt（リダイレクト先も）・X-Robots-Tag／meta の noarchive・noai・有料（`isAccessibleForFree:false`）・ロボット確認の画面・401/402/403/429 は取らず、理由を `news_body.reason` に残して `body_state=2`、**二度と試さない**。robots.txt そのものが読めない（5xx・通信の失敗）ときだけ、記録せずに 30 分あとへ延ばす。
  それ以外の失敗（404・時間切れ・本文が 200 文字未満）も「取れない」と記録して二度と試さない（一時的な失敗でも）。
- **保存の圧縮（9 章）**: 設定 `storage.compress_years`（既定 1・0 で無効）より古い記事の抜粋（`summary`）を Zstandard で `news_cold` へ移し、`summary` を空にして `cold=1`・索引からは抜粋を外す（題・概要・物・出どころは残る）。画面・API は抜粋を戻して出す（`store.hydrate`）。1 回 2,000 件。
  古い（圧縮した）記事の取り直しは何もしない。**圧縮しても DB のファイルは縮まない**（空いたページは次の記事が使う。縮めるには VACUUM が要るが、全体を書き直すので自動ではしない）。
- **SQLite のページのキャッシュ**を 256MB に（`NEWSHUB_SQLITE_CACHE_MB`。使った分だけ確保される。9 章の 256〜512MB の目安の下の端）。
- 試験の追加: `tests/test_search_storage.py`（16 件）。診断: 「検索と本文・圧縮」の節（索引の状態・本文の今日の使用・成否・取れない理由・圧縮の効果）。


### 8 章（検索と調査）の v0.6: ControlDeck の MPKR が使う検索の道具の API と、設計と違った点（2026-11-25・feat/retrieval-api）
MPKR 本体（計画・融合・reranker・埋め込み）は ControlDeck 側。ここは軽い道具だけで、既存を使い回した（全文は `searchindex`、物は `entities`、イベントは `events`、辺は `kg_view`、文書の索引は v0.7 前半の `docstore.doc_fts`）。
`retrieval.py`（種・PPR・根拠・調査）・`retrieval_router.py`（API）・`rcache.py`（キャッシュ・時間・大きさの上限）・`kg_view.py`（neighbors の拡張・辺の読み出し）。
- **`POST /retrieve/seeds`**: 問いの文から語を取り（形態素解析なし。ASCII の語・カタカナ・漢字の連なり、5 文字以上は 3 文字の窓も）、①全文＝既存の 2 つの索引（trigram・英語）を **OR** で引き BM25 を足す（`searchindex.search_any`。既存の検索は AND のまま）②物＝正規化のキーの完全一致・別名・「名前が問いの文に含まれる」・部分一致 ③イベント＝題の語・強く一致した物に関わるもの ④ニュース以外の文書＝`doc_fts` の BM25＋題の部分一致。
  返すのは種類つき（document・entity・event）の `items`（点数・`position`＝語が最初に出る場所〔題・概要・抜粋の文字位置と前後〕・日時・区分・段）。`limit` は**種類ごとの上限**。点数は種類をまたいで比べられない（種類の中の順は `rank`）。
  **設計と違う点**: 2 文字以下の語（日本語）は全文では引けない（trigram のため）ので、物の名前の照合にだけ使い、短い語しか無い問いは新しい題から LIKE（時間の上限つき）。`unsearched_short_terms` で知らせる。記事が `documents` にまだ対応づいていなければ `id` は null（`article_id` を返す）。
- **`POST /graph/neighbors` の拡張**（応答は互換。段ごとにまとめる方針のまま）: `direction`・`type_directions`（型ごとの向き。out＝入り口の物が主語・in＝逆向き。向きの無い型は常に両方）・`order`（weight・recent＝最後の日時が新しい順・evidence）・`only_contradicts`・`hub_k`（入り口の物 1 つにつき k 本まで・順は order。読み捨てたハブは `suppressed`）・物に `degree`（区分の範囲の辺の数）と `last_edge_at`・辺に `via`（入り口の物）。
  期限（`budget_ms`）を過ぎたら 2 段目以降へ進まない（`stopped`）。1 段目は必ず返す。
- **`POST /graph/ppr`**: 局所 PPR（Andersen–Chung–Lang の push 法。ラウンドごとに隣接をまとめて読む＝物ごとに問い合わせない）。ε・`max_nodes`・時間・押す回数の上限、辺の重みは確かさ（下限 0.05）か均等、向き、ハブは hub_k 本（既定 100）。戻りは score の大きい順と `via`（いちばん多く質量を送った物＝経路の手がかり）・`stats`（残りの質量 `residual_total` など）。
  **注意**: ε は「次数あたりの残り」の基準なので、ハブの種では質量の多くが残る（誤差の上限どおり）。順位は近い物の順として使い、厳密な値としては使わない。
- **`POST /retrieve/evidence`**: 物・主張・関係の id から根拠（引用・位置・文書の題・URL・日時・区分・AI_USE）を種類ごとの IN でまとめて返す。範囲外と無い id は同じ `missing`。
- **`GET /research?topic=`**: 同じテーマ（正規化して一致・包含）・類似のテーマ（2 文字の組の Jaccard）・`last_at`（前回）・`previous`。`research_records` に `sensitivity`（既定 public）を足した。
- **区分の強制**: `auth.read_user`（読むだけの POST にトークンを通す依存。書き込みには付けない）・`api_tokens.sens`（つないだときに許した区分）・`kg_router.scopes_for(user, confidential, sensitivity)`（範囲外は 403。黙って落とさない）。link のトークンは、**つないだときの設定 `link.allow_confidential`** が true のときだけ confidential を許される（読み取りだけの read トークンは常に public だけ）。管理者の session は全部。
  読む API は既定で public だけ（`confidential=true` か `sensitivity=["confidential"]` を付けたときだけ範囲を広げる）。**v0.5 の見落としも直した**: `/entities`・`/entities/{id}` は区分で絞っていなかった（機密の文書だけから作った物の名前が出た）。
- **キャッシュと上限**（`rcache.py`）: 応答の JSON を (道具・区分・本文・DB の版) のキーで LRU（32MB・5 分）。版は `PRAGMA data_version`（別の接続のコミットで変わる）＝どの経路で DB が変わっても無効になる。`X-Cache`・`X-Data-Version`。
  時間は `budget_ms`（既定 400・最大 3,000。ラウンド・段の間で見る）と SQLite の progress handler（期限の 3 倍で 503）。応答は 1MB を超えたら件数を減らして `truncated`・`size_limited`。
- **datetime の警告**: Python 3.12 の sqlite3 の既定の変換は、`text()` や生の SQL に datetime を直接束縛すると出る。`kg._sql_dt` など文字列で渡す形にして（書式は DateTime 列と同じ）0 にした。pytest の `filterwarnings` で再発したら落ちる。
- **まだ無いもの**: MMR・ブリッジ・reranker（ControlDeck 側）・意味（埋め込み）の検索（I8）・種の検索の 2 文字語の全文・つないだ相手の区分の範囲をあとから変える画面（いまはつなぎ直し）・本物の MPKR からの呼び出しでの評価（I0・I4）。

## 9. 書き込みと読み込みを最小に（最重要の要件の 1 つ）
- **Write Coordinator**: すべての永続化（記事・履歴・集計・知識・ジョブの状態・画像・ログ・WAL の checkpoint・FTS のマージ・バックアップ）を 1 つの係が束ね、まとめて書く。各処理が勝手にディスクを書かない。
- 既定: 記事のまとめ書き 30 分ごと・バッファ 1,000 件 / 128MB・単一の書き手・WAL の checkpoint は保存の直後と保守の時間だけ（自動の checkpoint を切る）・索引の更新はまとめて・ログはメモリ（リングバッファ）・アクセスのログは既定で切・一時ファイルはメモリ優先・DB の最適化とバックアップは指定の時間・QNAP の上の LLM は既定で切。
- **お休みモード**（既定 切。開始・終了の時刻）: 休止中の動き「集め続けてメモリに一時保存」「集める・分析・保存をすべて休む」「集め続けて上限のときだけ一括で保存」から選ぶ。厳格な休止では、ログ・DB・checkpoint・画像・索引・ジョブ・バックアップを含め、アプリが原因の書き込みを止める。
- **保存が済んでいないデータを、保存済みとして扱わない**（API の答えにも「未保存」と分かる印。ControlDeck へ返す差分は保存済みのものだけ）。停電・強制終了ではメモリの分が消えうる（RSS に残っていれば次の取得で取り直せる）。手で書いた大事なメモは「すぐ保存」を選べる。
- 読み込みも減らす（目安）: 最新の一覧 128MB・SQLite のページのキャッシュ 256〜512MB・検索の結果 128MB・トレンド 64〜128MB・知識の地図 128〜256MB・取得のバッファ 128MB・ベクトルは規模に応じて。通常の上限 1.5〜2GB、ベクトル込みで 4GB を候補に実機で決める（QNAP のほかのアプリのために 16GB を占有しない）。
- **書き込みの診断**（メモリのリングバッファで）: 直近 24 時間の読み書きの量・回数・最終保存と次の予定・WAL の大きさ・未保存の件数・プロセスの I/O（/proc/self/io）・お休み中の書き込みの検出と、その処理の特定。アプリの書き込みと NAS 全体の書き込みを分けて測る。

### 9 章の実装と、設計と違った点（v0.1・2026-11-24）

- **お休みモード**（設定 `rest`）: 3 つの動きは設計どおり。違う点 — ①「メモリに保持」には安全の上限（件数の 5 倍・容量の 2 倍）があり、超えたら**集めるのを止める**。② 休止中は、どの動きでも下ごしらえ・一言要約・まとめ・画像・checkpoint・1 日の要約の保存を止める（バックアップと集計はまだ無い）。③ **利用者の操作（設定の保存・ログイン・好み）は休止中でも書く**（書かないと休止を解けない）。書いた処理名は診断に残り、アプリが原因の書き込みがあれば「error」の知らせを出す。④ 休止が明けたら（書き手が終了時刻に起きて）まとめて保存する。

- **LLM の回数**はメモリが正で、ファイル（`llm-calls.json`）へはまとめ書きのときに書く。強制終了では最大 30 分の回数が戻りうる（上限をその分超えて呼ぶ可能性。SIGTERM では書く）。

## 10. 取得のエンジン
RSS 1.0・2.0・Atom の自動判別 / CSV と OPML の取り込み・書き出し / サイトからの RSS の発見 / **ETag・Last-Modified の条件付きの取得**（変わっていなければ本文を取らない）/ **更新の頻度に合わせた間隔（Adaptive Polling）** / 失敗・制限での間隔の延長（バックオフ）/ 重複の除去（URL・GUID・SimHash・意味の近さは ControlDeck）/ 出どころの種類（公式・報道・SNS・コミュニティ）/ 健全性の確認（止まった・XML の異常・失敗）。有料の記事・アクセスの制限・ロボット確認はすり抜けない。本文を保存できない記事は、取れる概要と元の URL だけ。

### 10 章の実装と、設計と違った点（v0.1・2026-11-24）
`backend/qnapnewshub/polling.py`（取得先ごとの状態・間隔）・`dedup.py`（重複）・`portability.py`（CSV・OPML）・`net.py` の `http_get_conditional`・`sources.py` の `FetchMeta`・`sourcemgr.py` の `infer_origin`。
- **条件付きの取得は RSS・Atom（`rss:` の取得先）だけ**。GitHub・Hacker News・フォーラム・Google ニュースの検索・一覧の巡回は、API かページなので対象外（毎回取る）。304 は成功に数え、履歴の `status` に 304 を残し、本文を解析しない。解析に失敗した応答の ETag は覚えない。
- **状態の置き場**: `news/fetch-state.json`（メモリが正。Write Coordinator のまとめ書きのとき、記事と同じ瞬間に書く）。強制終了では最大 30 分の分（ETag と次の予定）が戻る。再起動の直後は、保存した最後の取得の時刻から続ける（起動のたびに全部を取りに行かない）。
- **Adaptive Polling**: 新着が出た取得の間隔の指数平均の半分を次の間隔にする（出る頻度の 2 倍で見に行く）。履歴が無いうちは 1.5 倍ずつ伸び縮み。範囲は基準の 1/2〜8 倍。基準は取得先ごとの間隔か設定の既定。**固定**は設定 `fixed`（基準のまま。失敗でだけ延ばす）。「次の取得の予定」は最後の取得の時刻 ＋ いまの間隔（取得先の管理の画面）。
- **バックオフ**: 失敗・429・503（あらゆる失敗）で 基準 × 2^失敗回数、`Retry-After`（秒・日時）があればそれ以上、上限 24 時間。成功で戻る。診断の「止まった可能性」の判定は、いまの間隔（伸びた値）を基準に使う。
- **重複**: 設計の「意味の近さは ControlDeck」は未着手（v0.3）。実装したのは URL の正規化・GUID・SimHash。`news_items` に `canon_url`・`guid`・`simhash`・`dup_of` を足した（古い DB には初めて開いたときに列と索引を足す）。**同じ URL は 1 行**のまま（別の取得先が同じ URL を出したら、先に入った取得先の行へ。これは今までと同じ）。URL の揺れ・近い本文は別の行として保存し、`dup_of` で代表へ向ける。一覧・ホーム・まとめ・検索・ControlDeck への差分は代表だけ。代表には API で `also`（別の出どころの数）と `also_sources`。重複の行は、一言要約・下ごしらえ・画像の仕事に回さない。
- SimHash は**抜粋が 20 文字以上あれば抜粋だけ**（媒体ごとに題が違うため）、無いか短ければ題 ＋ 抜粋。文字の 3 つ組で 64bit。窓は DB の `fetched_at` で 48 時間。**同じ取得先の中は、近い重複としてまとめない**（週ごとのスレッドなど定型の題が多いため）。ハミング距離 3 以下は設計どおりだが、短い抜粋（100 文字ほど）では末尾に十数文字足されただけで 3 を超える（実データで確かめた）。厳しい分、見逃しは出るが誤ってまとめることは少ない。
- **CSV・OPML**: 取り込みは「確認の表（何も保存せず通信もしない）→ 通信確認してから追加（取れたものだけ有効）／そのまま追加（すべて無効）」。重複（同じ URL。http/https・www・末尾の / の違いは同じとみなす）は足さず数える。http の URL は https に直す（注記つき）。1 回の追加は 100 件まで（画面が 25 件ずつ送る）。書き出しは RSS・一覧の巡回・GitHub／Codeberg の Release のフィード・フォーラムの最新・Reddit（Hacker News・Hugging Face は URL が無いので含めない）。書き出しを取り込むと名前・分類・出どころ・間隔・有効が戻る（GitHub などは RSS として戻る）。OPML の DTD・実体は断る。
- **出どころの種類**: 設計の「SNS」は「論文」に置き換えた（利用者の指定: 公式・報道・ブログ・コミュニティ・論文・その他）。設定 `origins` に利用者が決めた値、無ければドメインの規則で推定（`infer_origin`）。画面は推定に「（推定）」を付け、変えられる。目録の既存の項目も推定。分類は設定 `categories`（CSV・OPML の分類）。

### 10 章の続き: 収集の connector の枠組み（v0.7 前半・2026-11-25・feat/connectors）
`connectors.py`（枠組み・予算・状態）・`connector_terms.py`（利用条件の記録）・`conn_impl.py`（新しい connector の取得と整形）・`docstore.py`（段 L0〜L4・昇格・論文の同定・Metric・L0 の検索）・`connectors_router.py`。ControlDeck の PLAN-integrated-knowledge 8 章の採用部分の前半。設計と違った点・決めたこと:
- **種類**は feed・api・historical・change・discovery・market（market は Metric の表と読みの API だけ。市場の connector は v0.8）。各 connector は 取得の間隔・1 日の件数・1 日の通信量（MB）・鍵（任意・secretbox）・設定・入／切を持つ。設定は `news/connectors.json`（利用者の操作で即時）、その日の使用・最後の結果・変化の検出の ETag と hash は `news/connector-state.json`（メモリが正・まとめ書きのとき書く）。
- **予算**: 1 日（UTC の日付）の件数または通信量が上限に達したら、その connector は止まり（途中なら次の通信の前に止まり、取れた分は保存）、診断の problems に「止めています」が出る。日が変わると戻る。「件数」は保存する文書・辺・Metric の点の合計。
- **既存の取得の載せ替え**: RSS 系は `feed`・GitHub の Release は `github`・arXiv の RSS は `arxiv`・HN は `hn`・HF の話題は `huggingface` の connector に属し（`for_source`）、`service._fetch_one` が取得の前に `gate`（入切・利用条件・予算・お休み）を通し、後で件数・受信量を数える。取得そのものは書き直していない。切にした connector の取得先は「見送り」として取得の履歴に残る。arXiv の RSS の記事は、記事のほかに**論文の文書（kind paper・L1・arXiv ID）**にもなる（ニュース側は news の文書として別に残る。両者は結ばない）。
- **利用条件**（`connector_terms.py`）: status は confirmed／partial／per_site／unconfirmed。公式の資料を読んだ範囲だけ書き、読めなかったものは「未確認」。**新しい connector は全部、既定で切**。unconfirmed（HN の検索）は、確認の明示（`terms_ack`）がないと入にできない（API は 422）。**例外**: 既存の取得を載せ替えた `hn` は利用条件が未確認だが、今までの取得を変えないため入のまま（診断に「未確認のまま入」と出す）。
- **保存の段**（documents.tier）: 0 発見・1 概要・2 本文・3 知識・4 分析。ニュースの文書は、既定 L1・本文を取り出せた→L2・要素の取り出しが済んだ→L3（`docstore.news_tiers`。まとめ書きの中で、保存された記事の分だけ即座に上げ、起動時と夜の文書の対応（`kg.sync_documents`）で取りこぼしを冪等に直す）。上げるだけ・理由と時刻は document_promotions と documents.tier_reason／tier_at。L4 と手での昇格は API（管理者）。
- **昇格の規則**（L0・L1 → L2。設定の promotion で 1 つずつ切れる）: チャンネルの語に合う（除外語のチャンネルは合わない）・ホットトピックの上位 10 の語を含む・監視の物（監視の GitHub のリポジトリ・監視のモデルの名前）を含む・スターの急増（1 日あたりの差が閾値以上。既定 100）・監視のモデルの派生版。**L2 に上がった非ニュースの文書の本文の取り出しは、この版では段の印だけ**（本文の取得は次の段。ニュースの記事は既存の bodies）。
- **論文の同定**: DOI・arXiv ID・OpenAlex ID・Semantic Scholar ID を `documents.ident`（1 つ。優先は arXiv > DOI > OpenAlex > S2 > URL）＋ `document_aliases`（別名）で 1 件にまとめる。arXiv の DOI（10.48550/arXiv.…）は arXiv ID として扱う。後から識別子が増えたら別名に足し、題・引用数を補い、段を上げる。引用・参考文献は `document_links`（文書どうしの cites。物どうしの relationships とは別）。
- **connector**: `github_discover`（検索 API: 直近の日数・最低のスター数・トピックごと。監視のリポジトリの `/repos/…` でスター数。スター数は日ごとに Metric `stars` へ、前の点との 1 日あたりの差を `stars_delta_1d` へ。同じ日の再取得は同じ点）・`hf_models`（新しいモデルを作者・タグ・pipeline で絞る。監視のモデルは関係ごとに `filter=base_model:<関係>:<id>` で引き、**サーバーの絞り込みが効かなくても、返った行を base_model のタグ・cardData で照合して一致したものだけ入れる**。量子化は GGUF・AWQ・GPTQ・EXL2・MLX・bnb・FP8 などをタグ・library・名前から）・`openalex`（分野 filter・直近の日数・書誌と引用数。要旨は取らない）・`crossref`（DOI だけの文書を 1 件ずつ解決。要旨は保存しない。解決できない DOI は二度と試さない）・`semanticscholar`（L2 以上の論文を種に、引用元と参考文献を 1 段、設定で 2 段目は引用数の多い数件だけ。隣の論文は L0）・`hn_search`（道具。問いに応じて 1 回ずつ。save なら L0）・`sitemap`（robots.txt の Disallow を守る・同じホストだけ・robots.txt が 5xx で読めないサイトは取らない・DTD を断る・gzip・新しい lastmod から max_urls 件・題は URL から）・`change`（ETag・Last-Modified の条件付き GET＋見える文字の hash。初回は基準だけ・1 ページ 15 分に 1 回まで・本文は保存しない）。
- **鍵**（GitHub・HF・OpenAlex・Semantic Scholar。任意）は secretbox（`connector.<id>.key`）。応答・診断・設定の API には値を出さず has_key だけ。GitHub の Release（既存）も鍵があれば付ける。
- **書き込み**は Write Coordinator（`stage_connector` → `docstore.apply`。1 トランザクション）。お休みモード・取得しない時間帯では動かさない。`news_loop` が 1 分ごとに間隔の来た connector を順に 1 回ずつ（同時には走らせない）。
- **L0 の検索**: ニュース以外の文書の題・要旨を `doc_fts`（trigram）に入れる（`GET /documents?q=`。3 文字未満は LIKE）。
- **API**: `/connectors`（管理者）・`PUT /connectors/{id}`・`/connectors/{id}/key`・`/connectors/{id}/run`・`/connectors/promotion`・`/connectors/hn_search/query`、`/documents`（検索・一覧）・`/documents/{id}`・`POST /documents/{id}/promote`（管理者）・`/documents/metrics/series`。
- **Crossref の polite プール・OpenAlex の mailto はメールアドレスが要る**ため使わない（公開のリポジトリ・利用者の情報を送らない）。Public プールのレートで 1 件ずつ。

## 11. 画面
ホーム（今日読むべき 10 件・日次の要約）・ニュース（リーダー・検索・絞り込み・放送局ほか 5 デザイン）・イベント・ナレッジ（知識カード・技術の辞典）・グラフ（知識の地図）・トレンド（急上昇・ランキング）・タイムライン・ヒートマップ（分類 × 期間の情報の密度）・比較（モデル・GPU・価格・性能）・マトリクス（技術の関係・互換性）・調査・ウォッチリスト・メモ・生成物・管理（取得先・AI・保存と省電力・書き込みの診断）。すべての画面で、期間・分類・出どころ・言語・根拠の種類で絞り込める。大きなデータを一度に送らず、サーバーが必要な範囲だけ返す。未実装の機能を実装済みのように表示しない。

### 11 章の実装と、設計と違った点（分析の画面・2026-11-24）
- ☰ のナビに「分析」。画面は上から: 期間（24 時間・7 日・30 日・90 日）・分類・言語の絞り込み → 数字のカード 4 枚（今日の記事・独立した記事・取得先・前の 7 日との比）→ 新着の傾向（積み上げの棒・分け方 5 種・粒度・重複を除く・凡例で絞り込み・下の帯で範囲）
  → ホットトピック（上位 10・新しい語・分野ごと。押すとニュースの検索 `/?q=` へ）→ 取得先の分析（表とヒートマップ）→ 期間の比較（今週と先週）→ 空き枠（知識の地図・物のノート）。
- ECharts 5.6.0（版を固定）は必要な部品だけを別のチャンクにし、分析の画面を開いたときに初めて読み込む。色は分類・言語・出どころごとに固定（チャンネルは設定の色、取得先は名前から一定）。ライト・ダークで文字・目盛り・枠も変える。
- **設計と違う点**: 設計の画面名「トレンド」「ヒートマップ（分類 × 期間）」「比較」は分析の 1 画面にまとめた。ヒートマップは取得先 × 日（分類 × 期間ではない）。一緒に出る分析・タイムライン・マトリクスは無い。
- ニュースのホームの上に、ホットトピックの上位 5 を小さく出す（押すと分析へ）。

## 12. もっと価値を上げる機能
- **ベンチマークの比較**: 数値を測定の条件ごとに保存し、自分の環境（R9700・ROCm・使っているエンジン）に近いものだけを比べる。条件の違うものを平均しない。
- **組み合わせの発見**: 別々の記事の技術を関連付け、ControlDeck の既存の実装の改善の候補を提案（提案と動作確認済みは分けて持つ）。ControlDeck の「導入候補の検出」と同じ系統。
- **ウォッチリストと変化**: 監視のテーマ（ローカル LLM・推論エンジン・AMD GPU・音声 AI・ゲーム・日本株・ONDO・セキュリティトークン など）ごとに、「前回から何が変わったか」を出す。
- **意見の違い**: 政治・経済・株式・暗号資産では、公式の発表・報道・専門家の分析・企業の見解・コミュニティの反応・未確認の情報を分け、確かめた事実と並べる。

## 13. 守り
- 記事の中の命令を実行しない（プロンプトインジェクション）。ニュースの分析の係は最小の権限（ControlDeck の道具・コマンドを呼べない）。
- SSRF（私的な IP・リダイレクトの各段）・XML（外部の実体・過大な展開を禁止）・HTML（スクリプトを無効に）・API の認証（読み取りと書き込みを分ける）・AI の出力は JSON Schema で検査・事実と主張に出どころ・トランザクションと冪等性・整合性のある世代のバックアップ・著作権（保存と書き出しの対象を制御）。

### 13 章の実装: 更新の守り（0.1.1）
アプリの更新（docs/UPDATE.md）は、Release の manifest の **Ed25519 署名**・名前・版・大きさ・sha256 をすべて確かめてからだけ入れる。取得は https・GitHub のホストだけ・リダイレクトの各段を検査・300MB まで。操作は管理者の session だけ（API トークンは不可）。試験用の差し替えは `NEWSHUB_INSTALL=qpkg-sim` のときだけ効く。
